## ユビキタス言語

| 用語 | 定義 |
|------|------|
| **LIGHTユーザー** | LIGHTプラン（無料）を利用しているユーザー |
| **PARTYユーザー** | PARTYプラン（有料）を利用しているユーザー |
| **チーム（TEAM）** | ゲーム配信者グループ。チームコードを入力することでチームに参加できる |
| **チームコード** | チームへの参加に使用する固有の英数字コード。Owner/Editorが設定画面から確認・リセットできる |
| **LIGHTプラン** | 無料プラン。参加チームメンバー上限2名、タスク月5件、コラボ月3件等の制限あり |
| **PARTYプラン** | 有料プラン。全機能無制限、バナー広告なし |

## 概要

ゲーム配信者（Twitch・YouTube）およびその制作チームを対象とした、配信者特化型チームスケジュール管理Webアプリ。配信枠の共有管理・コラボ日程調整・制作タスク管理を一元化し、配信者が本業（配信）に集中できる環境を提供する。

LIGHTプラン（無料）とPARTYプラン（有料）の2つのプランを提供し、ユーザーは無料で試用したうえでPARTYプランにアップグレードできる。課金はユーザーごとに行い、チームリーダーへの費用集中を防ぐ。

**対象ユーザー**:

- **プライマリ**: ゲーム配信者（個人〜小規模チーム、登録者数0〜1,000人規模）
- **チームメンバー**: 編集者・マネージャー・台本ライターなど（1〜5名）
- **将来的なターゲット**: 登録者数1,000人以上のストリーマー・Vtuber（フェーズ2以降）

## Clarifications

### Session 2026-05-12

- Q: 同時編集時のコンフリクト解決ポリシーは？ → A: 楽観的ロック＋競合警告（後から保存したユーザーに再読込を促す）
- Q: ターゲットユーザーの規模は？ → A: フェーズ1は0〜1,000人規模（プライマリ）
- Q: 認証方式は？ → A: メールアドレス+パスワードのみ。新規登録はプロダクト管理者発行のアクセストークンが必須。Google OAuthはカレンダー連携専用 *(2026-05-13 セッションで変更あり)*
- Q: カンバンのカラムはカスタマイズ可能か？ → A: 可能。Ownerが設定画面からカラム名・順序・色を管理できる
- Q: タスクデータのCSVエクスポートは必要か？ → A: 必要（Owner/Editor向け）
- Q: コラボ日程調整のスコープは？ → A: 相手はシステム外前提。共有URLをSNS（Discord等）で送付→相手が認証なしで回答→確定でURLを無効化
- Q: コラボ共有URLの有効期限は？ → A: セッション作成者が1〜30日の範囲でセッションごとに指定（入力必須）
- Q: アクセストークンの配布方法は？ → A: 管理画面でメールアドレスを指定するとシステムがトークン入り招待リンクを自動送信 *(2026-05-13 セッションで廃止)*
- Q: Googleカレンダー同期の失敗時の挙動は？ → A: 設定ページにエラーバナー表示＋手動再試行ボタン。サイレント失敗は不可
- Q: 通知のカスタマイズ粒度は？ → A: 4カテゴリ（コラボ関係/タスク/予定リマインダー/システム）ごとにアプリ内通知とプッシュ通知を個別ON/OFF（PARTYプランのみ）

### Session 2026-05-13

- Q: 認証方式を変更するか？ → A: Googleアカウント（Firebase Authentication Google OAuth2）でのログインに変更。アクセストークン方式・メールアドレス+パスワード認証は廃止
- Q: プランモデルを導入するか？ → A: LIGHTプラン（無料）とPARTYプラン（有料）の2プランを導入。Googleログイン後は自動的にLIGHTプランとなる
- Q: チーム参加方法は？ → A: メール招待方式を廃止。ユーザーが設定画面でチームコードを入力してチームに参加する方式に変更
- Q: 課金モデルは？ → A: ユーザーごとの個別課金（チームOwnerによる一括課金なし）でリーダーの経済的負担を軽減
- Q: チーム作成者のロールは？ → A: チームを作成したユーザーが初期Owner（管理者）となる
- Q: LIGHTユーザーのチーム新規作成権限は？ → A: LIGHTユーザーもチームを作成可能（メンバー2名上限が適用される）。ただし1ユーザーは1チームのみ所属でき、別チームに参加・作成する際は現在のチームを脱退してから行う。ログイン後はデフォルトでソロチームに所属する
- Q: LIGHTメンバーが所属するチームに3人目が参加しようとした場合の挙動は？ → A: 参加をブロックし「全員のPARTYプランへの加入が必要」と参加者に表示。同時に既存の全LIGHTメンバーにも「PARTYプランへのアップグレードが求められています」とシステム通知を送る
- Q: LIGHTプランの月次カウントのリセットタイミングは？ → A: 毎月1日 0:00（JST）にリセット（カレンダー月基準）
- Q: フェーズ1でのPARTYプランアップグレードCTAの動作は？ → A: 外部申し込みページ（Google Form等）にリンクする。希望者が一定数集まった段階でPARTYプランを解禁する方針
- Q: チームコードリセット後の旧コードへのアクセス挙動は？ → A: 即時無効化。旧コードで参加を試みると「無効なチームコードです」とエラー表示して参加ブロック

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 認証・チーム作成・参加 (Priority: P1)

新規ユーザーがGoogleアカウントでログインし、LIGHTプランとして開始する。チームを作成するかチームコードで既存チームに参加する。

**Why this priority**: 全ての機能の前提条件。チームが存在しなければスケジュールもタスクも管理できない。

**Independent Test**: ユーザーがGoogleログインからチーム作成またはチームコードでの参加まで完了でき、チームのダッシュボードにアクセスできる状態を単体で検証可能。

**Acceptance Scenarios**:

1. **Given** 未登録ユーザーがログインページにいる, **When** Googleアカウントでサインインする, **Then** アカウントが作成され自動的にLIGHTプランのソロチームに所属してオンボーディング画面に遷移する
2. **Given** 認証済みユーザーがオンボーディング画面にいる, **When** チーム名を入力して「チームを作成」を押す, **Then** 現在のソロチームを脱退し新チームが作成されユーザーがOwnerとして登録され、チームコードが自動生成される
3. **Given** 認証済みユーザーが設定画面にいる, **When** 既存チームのチームコードを入力して「参加する」を押す, **Then** 現在のチームを脱退した後そのチームのEditorとして参加できる（プラン制限を満たしている場合）
4. **Given** 認証済みユーザーがログアウトした, **When** 再度Googleアカウントでログインする, **Then** セッションが復元され所属チームのダッシュボードに戻る
5. **Given** PARTYプランのユーザーがチームを作成した, **When** PARTYプランの別ユーザーがチームコードで参加する, **Then** 現在のチームを脱退後にチームメンバーとして参加でき、3名以上のチームを構成できる

---

### User Story 2 - 共有カレンダー・スケジュール管理 (Priority: P1)

チームメンバー全員がリアルタイムで共有されるカレンダー上で、配信枠・動画投稿予定を作成・閲覧・管理する。

**Why this priority**: リスケるGGのコアバリュー。チーム全員がスケジュールを一目で把握できることが最重要。

**Independent Test**: 1人のユーザーがスケジュールエントリを作成すると、別デバイスにログイン中の別ユーザーが1秒以内にそのエントリを見れることを単体で検証可能。

**Acceptance Scenarios**:

1. **Given** Editorロールのユーザーがスケジュールページにいるとき, **When** 「配信を追加」から必須項目を入力して保存する, **Then** カレンダーにエントリが表示され、他のメンバーのカレンダーにも1秒以内に反映される
2. **Given** スケジュールエントリが存在するとき, **When** 同じ日時に別エントリを作成しようとする, **Then** 時間帯の重複を警告するメッセージが表示される（作成自体はブロックしない）
3. **Given** カレンダーが週ビューで表示されているとき, **When** 「月ビュー」ボタンを押す, **Then** 月単位のカレンダーに切り替わりエントリが正しく表示される
4. **Given** Viewerロールのユーザーがスケジュールページにいるとき, **When** スケジュールエントリを閲覧する, **Then** 詳細を閲覧できるが編集・削除ボタンは表示されない
5. **Given** EditorがGoogleカレンダー連携を設定した状態で, **When** Googleカレンダーに新しい予定が追加される, **Then** その予定がリスケるGGカレンダーに自動で同期される

---

### User Story 3 - 制作タスク管理（カンバン）(Priority: P1)

チームメンバーが制作タスク（撮影・編集・サムネ・告知等）を作成・アサイン・進捗管理する。LIGHTユーザーはタスク登録が月5件まで。

**Why this priority**: 配信スケジュールと並んで、制作サイドの業務可視化がプロダクトの第二の柱。

**Independent Test**: タスクをTODO→進行中→完了と進め、担当者変更もできることを単体で検証可能。

**Acceptance Scenarios**:

1. **Given** Editorがタスクボードページにいるとき, **When** 「タスクを追加」から必須項目を入力して保存する, **Then** TODOカラムにタスクが作成されアサインされたメンバーに通知が届く
2. **Given** PCブラウザでカンバンを閲覧しているとき, **When** タスクカードをドラッグして「進行中」カラムにドロップする, **Then** タスクのステータスが「進行中」に更新され即座に反映される
3. **Given** スマートフォンでカンバンを閲覧しているとき, **When** タスクカードの「ステータス変更」ボタンを押す, **Then** ステータス選択肢が表示されタップで変更できる
4. **Given** タスクが「完了」カラムに移動された状態で, **When** 全チームメンバーがカンバンを閲覧する, **Then** 全員が同じ最新のタスク状態を見ている
5. **Given** LIGHTユーザーが当月5件のタスクをすでに作成している, **When** 6件目のタスクを作成しようとする, **Then** 月間上限に達したことを伝えPARTYプランへのアップグレードを促すメッセージが表示される

---

### User Story 4 - コラボ日程調整 (Priority: P1)

配信者が他のチームとコラボ配信の日程調整を、アプリ内で完結させる。LIGHTユーザーはコラボ調整が月3件まで。

**Why this priority**: コラボ管理は現状DMや口頭で行われ記録が残らない。アプリ内完結が大きな差別化要因。

**Independent Test**: コラボ打診から日程確定・カレンダー自動登録までを単体で検証可能。

**Acceptance Scenarios**:

1. **Given** OwnerまたはEditorがコラボ管理ページにいるとき, **When** 「コラボを打診」からコラボ相手名・候補日程（最大5件）・有効期限を入力して送信する, **Then** 打診レコードが作成され共有URLが生成される。URLをDiscord等でコラボ相手に手動送付できる
2. **Given** コラボ相手が共有URLにアクセスした状態で（システム登録不要）, **When** 候補日程ごとにOK / NGを選択して「回答を送信する」を押す, **Then** 回答がFirestoreに記録され打診側チームのOwner/Editorに通知が届く
3. **Given** 打診側OwnerまたはEditorがコラボ詳細ページで回答を確認した状態で, **When** 希望日時を選んで「確定」を押す, **Then** 打診側チームのカレンダーにコラボスケジュールエントリが自動登録され共有URLが即時無効化される
4. **Given** 回答受付中のコラボセッションが存在するとき, **When** 打診側のOwnerまたはEditorが「キャンセル」を実行する, **Then** セッションがキャンセル済みになり共有URLが無効化される。確定済みの場合は打診側チームのカレンダーエントリも削除される
5. **Given** LIGHTユーザーが当月3件のコラボ調整をすでに作成している, **When** 4件目を作成しようとする, **Then** 月間上限に達したことを伝えPARTYプランへのアップグレードを促すメッセージが表示される

---

### User Story 5 - チームメンバー管理・ロール制御 (Priority: P1)

チームOwnerがメンバーのロール変更・削除を行い、適切なアクセス制御を維持する。

**Why this priority**: 編集権限の管理は安全なチーム運営の基盤。全ての機能の権限境界を定義する。

**Independent Test**: OwnerがメンバーのロールをEditor→Viewerに変更すると、そのメンバーが以前はできた操作ができなくなることを単体で検証可能。

**Acceptance Scenarios**:

1. **Given** OwnerがメンバーページでEditorを選択したとき, **When** ロールを「Viewer」に変更して保存する, **Then** そのメンバーは次のページリロード後に編集操作ができなくなる
2. **Given** OwnerがメンバーページにいてViewerを選択したとき, **When** 「チームから削除」を実行して確認する, **Then** そのメンバーはチームデータへのアクセスを失う
3. **Given** メンバーが削除されたとき, **When** そのメンバーにアサインされていた未完タスクが存在する, **Then** タスクのアサインが「未アサイン」状態になり、Ownerに通知が届く

---

### User Story 6 - 通知・PWA対応 (Priority: P2)

ユーザーがチーム内の重要なイベント（コラボ打診・タスク更新・配信リマインダー）を見逃さずに受け取る。LIGHTユーザーはシステム通知のみ受信可能。

**Why this priority**: スケジュールとタスク管理が整った後に、通知で運用効率がさらに向上する。

**Independent Test**: PARTYユーザーの配信1時間前リマインダーがアプリ内通知とプッシュ通知の両方で届くことを単体で検証可能。

**Acceptance Scenarios**:

1. **Given** ユーザーがアプリを開いているとき, **When** 自分宛にコラボ打診が届く, **Then** アプリ内通知バナーが表示され通知ベルのバッジ数が増える
2. **Given** PARTYユーザーがPWAとしてホーム画面からアプリを起動していて通知を許可しているとき, **When** 自分の配信開始1時間前になる, **Then** OSレベルのプッシュ通知が届く
3. **Given** ユーザーが通知一覧ページを開いたとき, **When** 未読通知を選択する, **Then** 対象の配信枠・タスク・コラボの詳細ページに遷移し通知が既読になる
4. **Given** LIGHTユーザーが通知設定ページにいるとき, **When** プッシュ通知を有効にしようとする, **Then** PARTYプランへのアップグレードが必要である旨が表示される

### Edge Cases

- ネットワーク切断中にスケジュール作成を試みた場合、どうなるか？（ローカルキャッシュ or エラーメッセージ）
- 複数デバイスで同時に同じエントリを編集した場合 → **楽観的ロック＋競合警告**: 後から保存したユーザーに「他のメンバーが編集しました。最新の内容を読み込んで再度編集してください」と警告を表示し、変更は破棄せず再確認を促す
- チームOwnerが脱退しようとした場合 → **所有権移譲が必要**: 別Editorに所有権を移譲するか、メンバーが自分のみであればチームを解散してソロチームに戻る
- 配信開始時刻と終了時刻が逆転して入力された場合のバリデーション
- タイムゾーンが異なるメンバーがいる場合の日時表示 → **JST固定**（フェーズ1）。全メンバーが同一タイムゾーンで日時を確認する
- コラボ打診相手が未登録のシステム外ユーザーの場合の扱い → **外部URL方式**。未登録者は共有URLから認証なしで回答できる専用フローを提供する
- チームからメンバーが削除された際の過去データの扱い → **完了タスク・過去スケジュールエントリは保持**。未完タスクのみ「未アサイン」状態に移行し、作成者名は「元メンバー」として表示する
- LIGHTユーザーもチームを新規作成可能（メンバー2名上限が適用）。ただし1ユーザー1チームのみ所属可能。別チーム参加・作成時は現在のチームを先に脱退する
- チームコードをリセット後に旧コードで参加を試みた場合 → **即時エラー**: 「無効なチームコードです」と表示して参加ブロック
- 3人目がLIGHTメンバー所属チームへの参加を試みた場合 → **参加ブロック＋全員通知**: 参加者に「全員のPARTYプランへの加入が必要」と表示し、既存の全LIGHTメンバーにも「PARTYプランへのアップグレードが求められています」とシステム通知を送る

## Requirements _(mandatory)_

### Functional Requirements

#### 認証・アカウント管理

- **FR-001**: 認証はFirebase AuthenticationのGoogle OAuth2で行わなければならない。メールアドレスとパスワードによる認証は提供しない
- **FR-002**: 初回Googleログイン時、ユーザーは自動的にLIGHTプランとして登録されなければならない
- **FR-003**: 認証セッションは自動的にリフレッシュされ、ユーザーは不意にログアウトされてはならない
- **FR-004**: 未認証ユーザーが保護されたページにアクセスした場合、ログインページへリダイレクトされなければならない
- **FR-005**: Google OAuth2認証で取得したアクセストークンは、Googleカレンダー連携にも再利用できなければならない（追加のOAuth認証フロー不要）

#### プラン管理

- **FR-P001**: システムはLIGHTプラン（無料）とPARTYプラン（有料）の2プランを提供しなければならない
- **FR-P002**: LIGHTプランには以下の制限を適用しなければならない:
  - 参加チームのメンバー上限: 2名まで（自分を含む）
  - スケジュール登録: 無制限
  - タスク登録: 月5件まで（当該ユーザーが当月作成したタスク数）
  - コラボ調整作成: 月3件まで（当該ユーザーが当月作成したセッション数）
  - 通知: システム通知カテゴリのアプリ内通知のみ（プッシュ通知・他カテゴリ不可）
  - バナー広告: あり
- **FR-P003**: PARTYプランのユーザーには全機能の利用制限はない。バナー広告は表示しない
- **FR-P004**: プランへの加入・変更はユーザーごとに行い、チームOwnerが他メンバーのプランを代理課金・管理する機能は提供しない
- **FR-P005**: メンバーが3名以上のチームに参加するには、全メンバーがPARTYプランである必要がある。条件を満たさない場合は参加をブロックし「全員のPARTYプランへの加入が必要です」と参加者に表示する。同時に既存チームの全LIGHTメンバーに「PARTYプランへのアップグレードが求められています」とシステム通知を送らなければならない
- **FR-P006**: LIGHTプランの月次上限に達した場合、当該操作をブロックしPARTYプランへのアップグレードを促す案内を表示しなければならない
- **FR-P006a**: LIGHTプランの月次カウント（タスク数・コラボ数）は毎月1日 0:00（JST）に自動リセットされなければならない
- **FR-P008**: フェーズ1において「PARTYプランへアップグレード」CTAをタップ・クリックすると、外部申し込みページ（Google Form等）へ遷移しなければならない。申し込みURLは設定で変更可能とし、URLが未設定の場合はボタンを非表示にする
- **FR-P007**: LIGHTプランのバナー広告はコンテンツの閲覧・操作を妨げない位置（ページ下部等）に表示しなければならない

#### チーム管理

- **FR-006**: 認証済みユーザーはチームを作成でき、自動的にOwnerロールが付与されなければならない
- **FR-007**: チームにはチームコード（固有の英数字文字列）が自動生成されなければならない。Ownerはチームコードをいつでもリセットできなければならない。リセット時に旧コードは即時無効化され、以後の参加試行には「無効なチームコードです」エラーを返す
- **FR-008**: ユーザーは設定画面でチームコードを入力してチームに参加できなければならない。参加前に現在のチームから自動脱退を確認するダイアログを表示する。チームのプラン制限を超える場合は参加をブロックする
- **FR-009**: チームコードで参加したユーザーはEditorロールが付与される。Ownerはその後ロールをEditor・Viewer間で変更できなければならない
- **FR-010**: システムは3つのロールを提供しなければならない: Owner（全権限）、Editor（スケジュール・タスクの作成・編集）、Viewer（閲覧のみ）
- **FR-011**: OwnerはメンバーのロールをEditor・Viewer間で変更できなければならない
- **FR-012**: OwnerはメンバーをチームからKickできなければならない（Owner自身は除く）
- **FR-013**: チームから削除されたメンバーはチームのデータに一切アクセスできなくなければならない
- **FR-014**: チームからメンバーが削除された場合、そのメンバーにアサインされていた**未完タスク**は「未アサイン」状態に移行しOwnerに通知されなければならない。完了済みタスク・過去のスケジュールエントリは保持され、作成者名は「元メンバー」として表示されなければならない
- **FR-015**: 1ユーザーが同時に所属できるチームは1つのみでなければならない。別チームに参加・作成する場合は現在のチームを先に脱退しなければならない
- **FR-015a**: 初回Googleログイン時、ユーザーは自動的にソロチーム（自分だけのメンバー）のOwnerとして登録されなければならない
- **FR-015b**: ユーザーはいつでも現在のチームを脱退できなければならない。ただしOwnerが脱退する場合は、別メンバーへの所有権移譲またはチーム解散を先に行わなければならない
- **FR-016**: Ownerは所有権を別メンバーに移譲するか、チームを解散してからチームを離れなければならない。所有権移譲なしの脱退はブロックする

#### スケジュール管理

- **FR-017**: Owner・EditorはスケジュールエントリをCRUD（作成・読取・更新・削除）できなければならない
- **FR-018**: Viewerはスケジュールエントリを閲覧のみ（CUD不可）できなければならない
- **FR-019**: スケジュールエントリは以下の項目を持たなければならない: タイトル（必須）、開始日時（必須）、終了日時（必須）、配信プラットフォーム（YouTube/Twitch/両方）、ステータス（予定/LIVE/終了/キャンセル）、説明、参加メンバー（複数選択）、コラボ相手（任意）
- **FR-020**: 動画投稿予定エントリは以下の追加項目を持たなければならない: 進捗（紐付くタスク）
- **FR-021**: スケジュールエントリの保存後、チームの全メンバーのカレンダーに1秒以内に反映されなければならない
- **FR-022**: カレンダーは週ビューと月ビューを切り替えて表示できなければならない
- **FR-023**: システムは同じ時間帯に複数エントリが存在する場合、視覚的に重複を示さなければならない（ブロックはしない）
- **FR-024**: ユーザーは自分のGoogleカレンダーをリスケるGGカレンダーと双方向同期できなければならない
- **FR-024a**: Googleカレンダー同期が失敗した場合（APIエラー・認証切れ・サービス障害等）、設定ページ上部にエラーバナーを表示し「再試行」ボタンで手動再同期できなければならない。サイレント失敗は許可しない
- **FR-024b**: Googleカレンダー連携の認証が切れた場合、バナーに「再認証が必要です」と表示し、Google再認証フローへ誘導しなければならない
- **FR-025**: 配信ステータスがLIVEに変更されると、エントリは視覚的にLIVE表示（赤バッジ+パルスアニメーション）されなければならない

#### 制作タスク管理

- **FR-026**: Owner・EditorはKanbanタスクをCRUDできなければならない
- **FR-027**: ViewerはKanbanタスクを閲覧のみできなければならない
- **FR-028**: タスクは以下の項目を持たなければならない: タイトル（必須）、担当者（任意）、締切日（任意）、カテゴリ（撮影/編集/サムネ/告知/その他）、所属カラム（必須）
- **FR-028a**: カンバンのカラム（進捗の種類）はOwnerが設定画面からカラム名・順序・色を追加・リネーム・削除・並び替えできなければならない
- **FR-028b**: デフォルトカラムは「TODO / 進行中 / 完了」の3つとする。カラムは最低1つ、最大10個まで設定できなければならない
- **FR-029**: タスクボードは設定されたカラムを左から順に表示しなければならない
- **FR-030**: PCブラウザではタスクカードをドラッグ&ドロップでカラム間移動できなければならない
- **FR-031**: モバイルではタスクカードのボタン操作でカラム変更できなければならない
- **FR-032**: タスクに担当者がアサインされた場合、担当者に通知が届かなければならない
- **FR-033**: タスクは動画投稿予定スケジュールエントリと紐付けられなければならない（任意）
- **FR-033a**: Owner・EditorはタスクボードのデータをCSVファイルとしてエクスポートできなければならない。エクスポートには全タスクの全項目（タイトル・担当者・カテゴリ・カラム・締切日・作成日・作成者）が含まれなければならない

#### コラボ日程調整

- **FR-034**: Owner・Editorはコラボ日程調整セッションを作成できなければならない。セッションにはタイトル・コラボ相手名（フリーテキスト）・候補日程（最低1件・最大5件）を含めなければならない
- **FR-035**: セッションを作成すると、コラボ相手が回答するための共有URLが自動生成されなければならない。このURLはDiscord等のSNSや任意のメッセージアプリで共有することを前提とする（メール自動送信は行わない）
- **FR-036**: 共有URLにアクセスしたコラボ相手は、システム登録・認証なしで各候補日時に対してOK/NG/代替日提案を記録できなければならない
- **FR-037**: 共有URLには有効期限が設定されなければならない。有効期限はセッション作成時に作成者が1〜30日の範囲で指定する（入力必須）
- **FR-038**: 日程が確定された時点で共有URLは即座に無効になり、以後のアクセスは「日程が確定されました」のメッセージのみ表示されなければならない
- **FR-039**: 日程が確定された時点で、打診側チームのカレンダーにコラボスケジュールエントリが自動登録されなければならない
- **FR-040**: コラボセッションのステータスは「回答受付中」「確定」「期限切れ」「キャンセル」で管理されなければならない
- **FR-040a**: Owner・Editorはいつでもコラボセッションをキャンセルできる。キャンセル後は共有URLが無効になり、確定済みの場合はカレンダーエントリも削除されなければならない

#### 通知

- **FR-041**: 通知は以下の4カテゴリに分類し、各カテゴリ内のイベントでアプリ内通知が生成されなければならない:
    - **コラボ関係**: コラボセッション作成・回答受信・日程確定・キャンセル
    - **タスク**: タスクへのアサイン・タスクのカラム変更（他者による変更）
    - **予定リマインダー**: カレンダーに登録された全スケジュールエントリの開始1時間前・15分前
    - **システム**: チーム参加・ロール変更・メンバーの削除
- **FR-041a**: PARTYユーザーは設定ページで通知カテゴリごとにアプリ内通知とプッシュ通知を個別にON/OFFできなければならない（4カテゴリ × 2種類 = 最大8つのトグル）
- **FR-041b**: LIGHTユーザーはシステム通知カテゴリのアプリ内通知のみ受信できる。他カテゴリやプッシュ通知の設定変更を試みた場合、PARTYプランへのアップグレードを促す案内を表示しなければならない
- **FR-042**: PARTYユーザーはPWAのプッシュ通知を許可・拒否できなければならない。OSレベルで拒否した場合はアプリ内でも許可を促すバナーを表示する
- **FR-043**: プッシュ通知を許可したPARTYユーザーには、アプリを閉じていてもユーザーがONにしているカテゴリのイベントでOS通知が届かなければならない
- **FR-044**: 通知は既読・未読を管理し、一覧ページで全履歴を確認できなければならない
- **FR-045**: 通知をクリック・タップすると、対象のスケジュールエントリ・タスク・コラボの詳細ページに遷移しなければならない

#### PWA・オフライン

- **FR-046**: アプリはPWAとしてAndroidのホーム画面に追加でき、インストールプロンプトが表示されなければならない
- **FR-047**: Service Workerは直近のスケジュールデータをキャッシュし、オフライン時でも直近データの閲覧ができなければならない
- **FR-048**: オフライン時に書き込み操作を試みたユーザーには、接続を要求するメッセージが表示されなければならない

### Non-Functional Requirements

- **NFR-001**: 初回表示（LCP）は4G回線のモバイル端末で3秒以内に完了しなければならない
- **NFR-002**: インタラクション応答（INP）は100ms以内でなければならない
- **NFR-003**: リアルタイムデータ更新はチームメンバー全員に1秒以内に反映されなければならない
- **NFR-004**: サービスの稼働率は99.5%以上でなければならない
- **NFR-005**: チームメンバーのデータは自チームのデータのみ読み書きできなければならない（クロスチームアクセス禁止）
- **NFR-006**: ロールに応じた書き込み権限制御はサーバーサイドで強制されなければならない（クライアントのみの制御は不可）
- **NFR-007**: 全通信はHTTPS経由でなければならない
- **NFR-008**: アプリはPC（Chrome/Edge/Firefox最新2バージョン）とAndroid Chrome（最新2バージョン）で動作しなければならない
- **NFR-009**: UIはWCAG 2.1 AA基準のアクセシビリティを満たさなければならない
- **NFR-010**: カレンダーと通知はJST（日本標準時）を基準として表示されなければならない（フェーズ1）
- **NFR-011**: プランの月次制限値はバックエンドで強制されなければならない（クライアント側のみの制御は不可）

### Key Entities

- **User**: 認証済みユーザー。displayName、email（Googleアカウント）、avatarUrl、plan（light/party）、planUpdatedAt、現在の所属チームID（単一）を持つ
- **Plan**: ユーザーのプラン情報。userId、planType（light/party）、monthlyTaskCount（当月作成タスク数）、monthlyCollabCount（当月作成コラボ数）を持つ。カウントは毎月1日 0:00（JST）にリセットされる
- **Team**: チーム。名前、OwnerID、チームコード（固有文字列）、作成日時を持つ。メンバーはサブコレクションで管理
- **TeamMember**: チームへの所属関係。userId、role（owner/editor/viewer）、displayName、avatarUrl、稼働ステータスを持つ
- **KanbanColumn**: カンバンカラム設定。チームID、カラム名、表示順序、色を持つ。Ownerが設定画面で管理する
- **ScheduleEntry**: スケジュールエントリ。タイトル、開始/終了日時、プラットフォーム、ステータス、説明、参加メンバーIDリスト、バージョン番号（楽観的ロック用）を持つ
- **Task**: 制作タスク。タイトル、カラムID（KanbanColumnへの参照）、カテゴリ、担当者ID、締切日時、作成者ID、紐付けスケジュールIDを持つ
- **CollabSession**: コラボ日程調整セッション。タイトル、コラボ相手名（フリーテキスト）、作成者ID、チームID、候補日程リスト、共有URL、URLトークン、有効期限、ステータス（回答受付中/確定/期限切れ/キャンセル）、確定日時を持つ
- **Notification**: 通知。受信者ID、タイプ、参照先エンティティ、既読フラグ、作成日時を持つ

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 新規ユーザーがGoogleログインからチーム作成・初期スケジュール登録まで完了するのに3分以内でできる
- **SC-002**: スケジュール更新は保存後1秒以内に全チームメンバーの画面に反映される
- **SC-003**: モバイル4G回線での初回ページ表示が3秒以内に完了する
- **SC-004**: タスクの作成・アサイン・ステータス変更が1分以内で完了できる
- **SC-005**: コラボ日程調整の共有URLを生成してから日程確定・カレンダー自動登録まで、打診側の操作は全てアプリ内で完結する
- **SC-006**: チームに参加する新規メンバーがチームコード入力から参加完了するまで1分以内でできる
- **SC-007**: アプリはAndroidホーム画面にPWAとしてインストールでき、ネイティブアプリに近い体験を提供できる
- **SC-008**: PARTYユーザーの配信開始15分前のプッシュ通知が、アプリを閉じていても届く
- **SC-009**: チームメンバーは他チームのデータに一切アクセスできない（セキュリティ要件）
- **SC-010**: 主要5ユーザーストーリー（認証・スケジュール・タスク・コラボ・チーム管理）が全て独立してデモ可能な状態でPhase 1を完了する

- **SC-012**: LIGHTユーザーとPARTYユーザーの両方がGoogleログインから2ステップ以内でチームに参加またはチームを作成できる

## Assumptions

- フェーズ1の対象ユーザーは日本語話者であり、UIは日本語のみで提供する（多言語対応はフェーズ2以降）
- チームの規模はフェーズ1では最大20名程度を想定する（大規模チームはフェーズ2以降でスケール検討）
- フェーズ1のタイムゾーンはJST固定とする（国際展開はフェーズ2以降）
- コラボ日程調整の相手は常にシステム外のユーザーを前提とする。生成された共有URLをDiscord等のSNSで送付し、相手が認証なしで回答する方式を採用する
- 認証はGoogleアカウント（Firebase Authentication Google OAuth2）のみとする。メールアドレス+パスワード認証は提供しない
- Google OAuth2で取得した認証情報はGoogleカレンダー連携にも再利用し、追加の認証フローを不要にする
- PARTYプランの決済基盤（Stripe等）の詳細設計はフェーズ2以降に行う。フェーズ1 MVPではプランデータ構造・月次カウント・UI制御の実装に留め、実際の課金処理は含まない。フェーズ1のアップグレードCTAは外部申し込みフォームへのリンクとし、希望者数に応じてPARTYプランを段階的に解禁する
- モバイル対応の優先プラットフォームはAndroid（PWA）。iOSのPWA対応改善はフェーズ2
- GoogleカレンダーAPI連携はフェーズ1 MVPに含むが、YouTube/Twitch API連携はフェーズ2
- オフライン書き込み（楽観的更新のキュー）はフェーズ1では対応しない（オンライン必須）
- ユーザーは安定したインターネット接続環境での利用を前提とする（低速回線への最適化はフェーズ2）
- チーム削除・解散フローはMVPに含めない（チームのアーカイブ/削除はフェーズ2以降）
- 配信スケジュールの繰り返し設定（毎週火曜など）はフェーズ1では対応しない
- 技術スタック: Next.js 14（App Router）/ TypeScript / Tailwind CSS / Zustand / Firebase（Auth・Firestore・Storage・Cloud Functions・FCM）/ Vercel / pnpm / ESLint+Prettier / Vitest / Playwright
