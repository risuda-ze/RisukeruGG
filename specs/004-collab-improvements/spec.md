# Feature Specification: コラボ機能改善・再調整

**Feature Branch**: `004-collab-improvements`  
**Created**: 2026-05-19  
**Status**: Draft  
**Scope**: spec 004（コラボ改善・修正）+ spec 005（コラボ再調整・復元）を統合

## User Scenarios & Testing

### User Story 1 - 候補日程の昇順ソート表示 (Priority: P1)

コラボ詳細画面および送信フォームで候補日程が日時の昇順で表示される。

**Why this priority**: 日程がバラバラに表示されると調整しにくい。一番近い候補から確認したい。

**Independent Test**: 3件の候補日程を「5/25」「5/20」「5/22」の順で登録し、詳細画面・送信フォームの両方で 5/20 → 5/22 → 5/25 の順で表示されることを確認。

**Acceptance Scenarios**:

1. **Given** 順不同で複数の候補日程が登録済み、**When** コラボ詳細画面を開く、**Then** 候補日程が日時の昇順で表示される
2. **Given** 公開コラボ送信フォームを開く、**When** 候補日程リストを確認、**Then** 日時の昇順で表示される

---

### User Story 2 - タイムゾーンバグ修正（JST 9時間ずれ） (Priority: P1)

コラボ作成フォームで入力した候補日程、および送信フォームで入力した代替日程が東京時間（JST: UTC+9）で正しく保存・表示される。

**Why this priority**: 現状 UTC で保存されており、表示時刻が 9 時間ずれるコア機能のバグ。

**Root Cause**: `datetime-local` の生文字列をそのまま Cloud Function に渡しており、Node.js 側で UTC として解釈される。

**Independent Test**: 「2026-05-25 15:00」を候補日程として登録し、詳細画面に「5月25日 15:00」と表示されることを確認。

**Acceptance Scenarios**:

1. **Given** コラボ作成フォームで「2026-05-25T15:00」を入力して作成、**When** 詳細画面を確認、**Then** 「5月25日（月）15:00」と表示される
2. **Given** 公開送信フォームで代替日程に「2026-05-26T18:00」を入力して送信、**When** 詳細画面を確認、**Then** 「5月26日（火）18:00」として候補に追加される

---

### User Story 3 - コラボ送信フォームのレスポンシブ対応 (Priority: P1)

スマートフォン（375px 幅）でコラボ公開送信フォームを操作できる。

**Why this priority**: 送信フォームは外部参加者がモバイルでアクセスする。ボタンのはみ出しはコア体験を損なう。

**Independent Test**: 375px 幅のブラウザで公開送信フォームを開き、全要素が横スクロールなしに表示・操作できることを確認。

**Acceptance Scenarios**:

1. **Given** 375px 幅のブラウザ、**When** コラボ公開ページを開く、**Then** OK/NG/未定ボタンが1行で表示され横スクロールが発生しない
2. **Given** 375px 幅のブラウザ、**When** datetime-local 入力を操作、**Then** 入力フィールドが画面幅に収まり操作できる

---

### User Story 4 - 送信メモをコメントとして追記 (Priority: P2)

コラボ送信フォームで「メモ」を入力して送信すると、そのメモがコラボ詳細画面の「コメント / メモ」セクションに追加される。

**Why this priority**: 現状メモはレスポンスデータにしか残らず、チーム側がコメント欄で確認できない。

**Independent Test**: 送信フォームで「当日は夜のみ可能です」とメモして送信後、詳細画面コメント欄に「田中 太郎: 当日は夜のみ可能です」と表示されることを確認。

**Acceptance Scenarios**:

1. **Given** 送信フォームでメモに「当日は夜のみ可能です」を入力して送信、**When** 詳細画面のコメントセクションを確認、**Then** 送信者名とメモ内容が追加されている
2. **Given** 送信フォームでメモを入力せずに送信、**When** 詳細画面のコメントセクションを確認、**Then** コメントは追加されない

---

### User Story 5 - 候補日程の編集・削除 (Priority: P2)

コラボ詳細画面で、候補日程の日時を変更・削除できる。

**Why this priority**: 候補日程を間違えた場合や変更が必要な場合に修正できないと使い勝手が悪い。

**Independent Test**: 詳細画面で候補日程の編集・削除ボタンを操作し、変更が反映されることを確認。

**Acceptance Scenarios**:

1. **Given** 候補日程が3件登録済み、**When** 1件を編集して日時を変更、**Then** 変更後の日時が反映される
2. **Given** 候補日程が3件登録済み、**When** 1件を削除、**Then** 残り2件になる
3. **Given** 候補日程が1件のみ、**When** 削除ボタンを確認、**Then** ボタンが無効化されている

---

### User Story 6 - 確定済みコラボの再調整 (Priority: P1)

日程確定後に都合が変わった場合、確定済みコラボを「調整中（open）」の状態に戻して再度日程調整できる。

**Why this priority**: コラボ確定後の日程変更は頻繁に発生する。現状は削除して一から作り直すしかない。

**Independent Test**: 確定済みコラボの詳細画面で「再調整する」をクリックし、ステータスが「調整中」に戻り、候補日程・参加者情報が残っていることを確認。

**Acceptance Scenarios**:

1. **Given** コラボが `confirmed` ステータス、**When** 「再調整する」ボタンをクリックし確認ダイアログで承認、**Then** ステータスが `open` に戻り、確定日・リンクスケジュールがクリアされる
2. **Given** 確定時に自動作成されたスケジュールが存在する、**When** 再調整を実行、**Then** そのスケジュールは削除される
3. **Given** 再調整後の詳細画面、**When** 表示を確認、**Then** 候補日程・参加者・内容・コメントは元の状態で残っている

---

### User Story 7 - 確定済みコラボの複製 (Priority: P2)

確定済みコラボと同じ相手・タイトルで、日程だけ異なる新しいコラボ調整を素早く作成できる。

**Why this priority**: 定期コラボや再スケジュールで毎回タイトル・相手名を入力し直す手間を省く。

**Independent Test**: 確定済みコラボの詳細画面で「コピーして新規作成」をクリックし、タイトル・参加者・内容が引き継がれた状態でフォームが表示されることを確認。

**Acceptance Scenarios**:

1. **Given** 確定済みコラボの詳細画面、**When** 「コピーして新規作成」ボタンをクリック、**Then** タイトル・参加者・内容を引き継いだ状態でコラボ作成フォームが開く
2. **Given** 複製フォームで候補日程を入力して作成、**When** 完了、**Then** 元のコラボとは別の新規コラボセッションが作成される

---

### Edge Cases

- 候補日程のソートは表示のみ（Firestore保存順は変更しない）
- タイムゾーン変換はブラウザの `new Date(localStr).toISOString()` で実施（タイムゾーンをハードコードしない）
- 候補日程を削除した際、その日程インデックスに紐づく `participantResponses` エントリも再インデックスする
- 候補日程が1件の場合、削除ボタンを無効化する（最低1件必須）
- メモが空白のみの場合はコメントとして追記しない
- `linkedScheduleId` が指すスケジュールが削除済みの場合、再調整時はスキップしてエラーにしない
- `cancelled` ステータスのコラボに再調整・複製ボタンは表示しない

## Requirements

### Functional Requirements

**バグ修正・仕様変更**:
- **FR-001**: コラボ詳細画面の候補日程は日時の昇順でソートして表示しなければならない
- **FR-002**: コラボ送信フォーム（公開ページ）の候補日程は日時の昇順でソートして表示しなければならない
- **FR-003**: `CollabForm` の `proposedDates` は ISO 8601 UTC 文字列に変換してから Cloud Function へ渡さなければならない
- **FR-004**: `CollabResponseForm` の `alternativeDate` は ISO 8601 UTC 文字列に変換してから Cloud Function へ渡さなければならない
- **FR-005**: コラボ送信フォームは 375px 幅のビューポートで横スクロールなしに表示できなければならない
- **FR-006**: コラボ送信フォームの OK/NG/未定ボタンは 375px 幅でも1行に収まらなければならない

**追加機能（コラボ改善）**:
- **FR-007**: コラボ送信フォームでメモを入力して送信した場合、`respondToCollab` Cloud Function がそのメモを `comments` 配列に追記しなければならない
- **FR-008**: 候補日程（`isOpen && canEdit` 時）に削除ボタンを表示し、削除時に `participantResponses` を再インデックスしなければならない
- **FR-009**: 候補日程（`isOpen && canEdit` 時）に編集ボタンを表示し、インライン日時入力で変更・保存できなければならない
- **FR-010**: 候補日程が1件の場合、削除ボタンは無効化しなければならない

**追加機能（再調整・復元）**:
- **FR-011**: 確定済み（`confirmed`）コラボ詳細画面に「再調整する」ボタンを表示しなければならない
- **FR-012**: 「再調整する」実行前に確認ダイアログを表示しなければならない
- **FR-013**: 再調整を実行した際、ステータスを `confirmed` → `open`、`confirmedDate` を null、`linkedScheduleId` を null に変更し、確定時に作成されたスケジュールを削除しなければならない
- **FR-014**: 再調整後、候補日程・参加者・タイトル・内容・コメントは保持しなければならない
- **FR-015**: 確定済みコラボ詳細画面に「コピーして新規作成」ボタンを表示しなければならない
- **FR-016**: 「コピーして新規作成」では、タイトル・参加者・内容を引き継いだコラボ作成フォームを開かなければならない

### Key Entities

- **CollabSession**: `status`（`open` / `confirmed` / `cancelled`）、`confirmedDate`、`linkedScheduleId`、`proposedDates: Date[]`、`participantResponses: Record<respondentKey, Record<dateIndex, 'ok'|'ng'|'pending'>>`、`comments: CollabComment[]`
- **CollabComment**: `{id, authorId, authorName, text, createdAt}` — 送信者のメモを外部コメントとして追記
- **ScheduleEntry**: 確定時に自動作成。再調整時に削除対象となる

## Success Criteria

### Measurable Outcomes

- **SC-001**: 修正後、候補日程が日時の昇順で表示される（手動テストで確認）
- **SC-002**: 修正後、JST で入力した日程が 9 時間ずれなく正確に保存・表示される
- **SC-003**: 375px 幅のブラウザでコラボ公開フォームが横スクロールなしに操作できる
- **SC-004**: 再調整の操作が「ボタン → 確認ダイアログ → 実行」の 2 ステップで完了する
- **SC-005**: 複製フォームでは初回作成に比べて入力項目が 50% 以下になる

## Assumptions

- 候補日程の編集・削除・再調整・複製は `canEdit`（Owner/Editor）権限のみ実行可能
- 再調整後の `participantResponses` はデフォルトで保持する（前回回答の参考にできるため）
- タイムゾーン変換は `new Date(localStr).toISOString()` で実施。サーバー環境（JST）のハードコードは行わない
- 複製はクライアント側のフォームプリフィルのみ（既存 `createCollabSession` Cloud Function を再利用）
- `collabs/page.tsx` は独自インラインフォームを持つため `CollabForm.tsx` は変更対象外
