# 仕様書: チーム権限バグ修正 & メンバースケジュール閲覧機能

**Branch**: `011-team-permission-member-schedule` | **Date**: 2026-05-24  
**Status**: Draft

## 概要

チーム管理・権限まわりの4つのバグを修正し、スケジュール画面でチームメンバーの予定を参照できる機能を追加する。

---

## バグ修正

### バグ 1: チーム内にオペレーター権限を持つユーザーが複数存在できない

#### 症状
- チーム管理画面のロール変更UIで、既にオペレーターであるメンバーのロール変更ドロップダウンが表示されない
- ロール変更ダイアログで「オペレーターへ昇格すると、現在のオペレーターはメンバーに降格されます」と表示され、強制的に1名のみになる

#### 原因
- `src/app/(protected)/team/page.tsx:288` でロール変更UIを `member.role !== 'operator'` の場合のみ表示しており、複数オペレーターが想定されていない
- `src/components/team/RoleChangeDialog.tsx:41` で昇格前に必ず現在のオペレーターを降格する実装になっている
- `src/app/(protected)/team/page.tsx:467` で `currentOperatorId={myMember?.userId}`（自分自身）を渡しているため、昇格操作を行うと自分がメンバーに降格される

#### 副作用 (バグ2の原因)
オペレーターが他のメンバーをオペレーターに昇格させようとすると:
1. まず自分（currentOperatorId）をメンバーに降格 → Firestore 書き込み成功
2. 次に対象メンバーをオペレーターに昇格しようとするが、自分の権限がすでに `member` に変わっているため Firestore Security Rules（`isTeamOwner`）が拒否
3. 結果: チームにオペレーターが0名の状態になり、`kanbanColumns` の書き込み（`isTeamOwner` 必須）が全員に対して失敗する

#### 受け入れ基準
- [ ] チーム内に複数のオペレーターを設定できる
- [ ] 既存のオペレーターを降格させなくても、別のメンバーをオペレーターに昇格できる
- [ ] ロール変更ダイアログから「オペレーターになると既存オペレーターが降格」という強制動作を除去する

---

### バグ 2: オペレーター権限ユーザーがカテゴリ・カラムを作成できない

#### 症状
- 設定画面でスケジュールカテゴリ・タスクカテゴリ・カンバンカラムの追加ボタンを押すと「○○の追加に失敗しました」が表示される

#### 原因
バグ1の副作用により、昇格操作後にチームのオペレーターが0名になることがある。Firestore Security Rules の `kanbanColumns` は `isTeamOwner`（オペレーター以上）を要求するため、全員がアクセス不能になる。

#### 受け入れ基準
- [ ] オペレーター権限のユーザーがスケジュールカテゴリを追加できる
- [ ] オペレーター権限のユーザーがタスクカテゴリを追加できる
- [ ] オペレーター権限のユーザーがカンバンカラムを追加できる
- [ ] バグ1の修正後、オペレーターが0名にならないことで自然解決する

---

### バグ 3: 別チームに参加する際に現在のチームからの脱退確認がない

#### 症状
- 設定/チーム管理画面の「別のチームに所属する」フォームで、チームコードを入力して参加すると、確認なしに現在のチームに所属したまま追加参加される
- ユーザーが「今のチームから出たい」場合の手段が別途必要

#### 要件
- 参加時に「現在のチームに所属したままにしますか？」と確認ダイアログを表示する
- 「いいえ（脱退する）」を選択した場合は、現在のチームから脱退してから新しいチームに参加する
- 「はい（そのまま）」を選択した場合は既存動作（複数チーム所属）を維持

#### 受け入れ基準
- [ ] チームコードを入力して参加ボタンを押すと確認ダイアログが表示される
- [ ] 「現在のチームから脱退してから参加」を選択すると、旧チームから脱退後に新チームに参加する
- [ ] 「そのまま参加」を選択すると、既存動作（複数チーム所属）のまま新チームに参加する
- [ ] チームに所属していない（ソロ）状態では確認ダイアログを表示しない

---

### バグ 4: サイドバーの「チームの切り替え」から切り替えができない

#### 症状
- サイドバーの「チームの切り替え」ボタンをクリックしてチームを選択しても、表示が切り替わらない

#### 原因（推定）
- `src/components/layout/TeamSwitcher.tsx` の `handleSwitch` は `switchActiveTeam` Cloud Function を呼び出す
- Cloud Function は `users/{uid}.currentTeamId` を更新し、auth store のリアルタイムリスナーが反応する
- しかし、タスク・スケジュール等の他ストアが新チームのデータに再購読されない可能性がある
- または `teamIds.length <= 1` の条件によりコンポーネント自体が非表示になっているケースがある

#### 受け入れ基準
- [ ] 複数チームに所属するユーザーがサイドバーから別のチームに切り替えられる
- [ ] 切り替え後、スケジュール・タスク・メンバー一覧が新チームのデータに更新される
- [ ] 切り替え後、現在のチーム名がサイドバーに正しく表示される

---

## 追加機能: スケジュール画面でメンバーの予定を参照

### 概要

スケジュール画面で「自分のGoogleカレンダー」「チームメンバーの予定」「チームの予定」の3種類を表示できるようにする。

### User Story 1 - ログイン時にGoogleカレンダーの予定をチームに同期 (Priority: P1)

ユーザーがログインしたとき、そのユーザーのGoogleカレンダーの予定（時間情報のみ）をチームのFirestoreに保存する。これにより、そのユーザーがオフライン・ログアウト中でも、チームメンバーが予定時間を参照できるようになる。

**Why this priority**: 他のメンバースケジュール表示機能の前提条件。

**Independent Test**: 「ログインするとFirestoreの `teams/{teamId}/memberCalendars/{userId}/events` にユーザーの予定が保存される」

**Acceptance Scenarios**:

1. **Given** Googleカレンダー連携済みユーザーがログインする, **When** ログイン処理が完了する, **Then** 当日〜2週間先のGoogleカレンダーイベントが `teams/{teamId}/memberCalendars/{userId}/events` に保存される
2. **Given** イベントがFirestoreに保存される, **When** タイトルが確認される, **Then** タイトルは「{ユーザーの表示名} の予定」となっている（元のタイトルは保存しない）
3. **Given** Googleカレンダー未連携ユーザー, **When** ログインする, **Then** 予定の同期は行われない

---

### User Story 2 - スケジュール画面でメンバーの予定を表示 (Priority: P1)

スケジュール管理画面で、チームメンバーが事前に同期した予定を確認できる。

**Why this priority**: チームの空き時間調整に直接必要な機能。

**Independent Test**: 「スケジュール画面に『メンバーの予定』トグルがあり、ONにするとメンバーが同期した予定が表示される」

**Acceptance Scenarios**:

1. **Given** スケジュール画面を開く, **When** 「メンバーの予定」が有効になっている, **Then** チームメンバーが同期した予定が「{ユーザー名} の予定」というタイトルでカレンダーに表示される
2. **Given** メンバーBがログアウト中, **When** メンバーAがスケジュール画面を開く, **Then** BがFirestoreに同期済みの予定は表示される
3. **Given** 「チームの予定」が有効, **When** カレンダーを表示する, **Then** `teams/{teamId}/schedules` に登録されたチームの予定も表示される

---

### User Story 3 - 自分の予定とメンバーの予定の重複を排除 (Priority: P2)

自分のGoogleカレンダーから直接取得した予定と、Firestoreに保存された「自分の予定」が重複して表示されないようにする。

**Why this priority**: UX改善。P1機能が動作後に修正できる。

**Independent Test**: 「自分の予定はGoogleカレンダーからの1件のみ表示され、Firestore保存版と重複しない」

**Acceptance Scenarios**:

1. **Given** 自分のGoogleカレンダーと「メンバーの予定（自分）」の両方が有効, **When** カレンダーを表示する, **Then** 同一の予定は1件のみ表示される（Googleカレンダーの直接取得を優先）

---

### User Story 4 - AIがメンバー・チームの予定を参照して回答 (Priority: P3)

AIチャット（`/chat`）でユーザーが「〇〇さんの予定は？」「チームの今週の予定は？」などと質問したとき、AIがFirestoreのメンバーカレンダーとチームスケジュールを参照して回答できる。

**Why this priority**: 利便性向上。他の機能が安定してから実装。

**Independent Test**: 「AIに『今週のチームメンバーの予定を教えて』と聞くと、Firestoreのデータを元に回答する」

**Acceptance Scenarios**:

1. **Given** AIチャット画面, **When** 「今週メンバーが空いてる時間は？」と質問する, **Then** AIがFirestoreのmemberCalendarsとteam schedulesを参照して回答する
2. **Given** AIチャット画面, **When** 特定のメンバーの予定を質問する, **Then** そのメンバーがFirestoreに同期した予定を参照して回答する

---

### Edge Cases

- Googleカレンダー連携を解除したユーザーのFirestoreデータはどうなるか？（定期削除は対象外）
- チームから脱退したユーザーのmemberCalendarデータはどうなるか？（アクセス制御のみ対応）
- memberCalendarのイベント数が多い場合（最大250件/ユーザー）のパフォーマンス
- 複数チームに所属するユーザーのlogin同期は全チームで行うか？（現在のアクティブチームのみ対応）

---

## Requirements

### Functional Requirements

- **FR-001**: チーム内に複数のオペレーターを設定できること
- **FR-002**: ロール変更時に既存オペレーターを強制降格しないこと
- **FR-003**: オペレーターがカテゴリ・カラムをCRUDできること
- **FR-004**: 別チームへの参加前に現在チームからの脱退確認ダイアログを表示すること
- **FR-005**: サイドバーからチームを切り替えると全データが新チームに更新されること
- **FR-006**: ログイン時にGoogleカレンダーの予定（タイトル: `{ユーザー名} の予定`、startAt/endAt のみ）をFirestoreに保存すること
- **FR-007**: スケジュール画面でメンバーの予定を表示・非表示切り替えできること
- **FR-008**: メンバーがログアウト中でもそのメンバーの保存済み予定を参照できること
- **FR-009**: 自分のGoogleカレンダー直接取得とFirestore保存版の重複表示を防ぐこと
- **FR-010**: AIチャットがmemberCalendarsとteam schedulesを参照して回答できること

### Key Entities

- **MemberCalendarEvent**: ユーザーのGoogleカレンダーから同期された予定。タイトル（`{username} の予定`）・startAt・endAt・sourceEventId（重複排除用）を持つ。`teams/{teamId}/memberCalendars/{userId}/events/{eventId}` に保存
- **TeamMember（変更）**: 複数オペレーターを許容（既存の `role: 'operator' | 'member' | 'rom'` の意味を変更しないが、1チームに複数オペレーターを許可）

---

## Success Criteria

- **SC-001**: バグ1〜4が修正され、チーム管理の基本操作が全て正常に動作する
- **SC-002**: オペレーターが0名になるシナリオが発生しない
- **SC-003**: スケジュール画面でメンバーの予定が表示できる
- **SC-004**: ログアウト済みメンバーの予定もFirestoreから参照できる
- **SC-005**: AIが「チームの予定」「メンバーの予定」を参照した回答を返せる

## Assumptions

- 複数オペレーター許可後も、チーム解散・メンバー削除の操作は全オペレーターが実行可能
- memberCalendarの同期範囲: ログイン時点から2週間先のイベントを対象とする
- memberCalendarの更新: ログイン時のみ。定期バックグラウンド同期は対象外（既存のCloud Functionは別途動作）
- 複数チームに所属するユーザーのmemberCalendar同期: ログイン時のアクティブチームのみ対象
- memberCalendarイベントの保存上限: 1ユーザーあたり最大250件（Googleカレンダー API の取得上限）
- AIがアクセスするmemberCalendarの範囲: 当日〜2週間先
