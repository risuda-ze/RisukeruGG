**作成日**: 2026-11-22
**状態**: 設計（仮決定を含む）・未実装（Issue #211）

## 変更名

新タスク構造（親子タスク）の導入と、ガントチャート(β)画面の追加

## 目的

配信チームが、複数の動画・配信の作業が「いつからいつまで」重なっているかを 1 画面で見られるようにする。

現行は単発の作業をカンバン（`/tasks`）、動画 1 本の作業をブリーフと工程（`/briefs`）で別々に持ち、どちらも開始日を持たない。親子にできる 1 つのタスク構造へまとめ、その上にガントチャートを置く。

## 対象範囲

本書は段階の 1 つ目（β）を扱う。β では新しいコレクションに新しい画面から作ったタスクだけを扱い、既存の画面とデータには触れない。

- 含む
  - 新タスク構造（コレクション `taskItems`、変更の記録）と操作層
  - 進め方（プレイブック）からの親子タスクの一括生成
  - ガントチャート(β)画面（PC・モバイル）、タスクの作成、タスク詳細ドロワー
  - 進め方の工程定義への所要日数・カテゴリ既定値の追加
  - カテゴリ削除・状態削除・所属者の退出時に、新タスクの参照を既存のタスクと同じように片付ける処理
- 含まない（別 Issue）
  - ブリーフ機能の新タスク構造への置き換え（Discord スレッド・通知・ダイジェスト、AI ツール、`/team/[uid]` の「担当中の工程」）
  - 既存データ（`tasks`、`briefs`、`steps`）の移行と、旧画面（`/tasks`、`/briefs`）の削除
  - 新タスクのコメント機能（要否を #246 で検討中）
  - 新タスクの一覧画面、ダッシュボードの完了率の切り替え
  - カレンダーの終日の持ち方をタスクに揃える修正

## 設計

### データモデル

#### `teams/{teamId}/taskItems/{itemId}`（新規）

型は `src/types/taskItems.ts` に新規に定義する。

| フィールド                       | 型                              | 用途                                                                        |
| -------------------------------- | ------------------------------- | --------------------------------------------------------------------------- |
| `id`                             | string                          | ドキュメント ID                                                             |
| `title`                          | string                          | タスク名（1〜100 文字）                                                     |
| `columnId`                       | string                          | 状態。`TaskStatus.id` を参照する                                            |
| `categoryId`                     | string \| null                  | カテゴリ。ガントでアイコン表示と検索に使う                                  |
| `description`                    | string \| null                  | 説明                                                                        |
| `assigneeId`                     | string \| null                  | 担当者の UID                                                                |
| `startAt`                        | timestamp \| null               | 開始日時。バーの始点                                                        |
| `dueAt`                          | timestamp \| null               | 締切日時。バーの終点                                                        |
| `parentId`                       | string \| null                  | 直近の親。最上位は null                                                     |
| `ancestorIds`                    | string[]                        | 最上位から直近の親までの ID。配下全体の取得と、祖先の日時を広げる処理に使う |
| `order`                          | number                          | 兄弟の中での並び順                                                          |
| `playbookId` / `playbookVersion` | string \| null / number \| null | 生成元の進め方と版。進め方から生成した親だけが持つ                          |
| `linkedScheduleId`               | string \| null                  | 関連するスケジュール。β の画面では扱わない                                  |
| `createdBy`                      | string                          | 作成者の UID。作成時に本人の UID を入れ、以後は変更しない（TE-018）         |
| `updatedBy`                      | string                          | 最終更新者の UID（TE-018）                                                  |
| `createdAt` / `updatedAt`        | timestamp                       |                                                                             |

制約

- `startAt` と `dueAt` は両方 null か、両方値を持つ。`startAt <= dueAt`
- 秒未満は 0 に切り捨てて保存する
- 日時を持つタスクの祖先は、全員が日時を持つ。日時を持つ子は、親の `startAt` 〜 `dueAt` の内側にある
- 日時を持つ子がいるタスクの日時は、空にできない
- `ancestorIds` に自分の ID を含めない。親に選べるのは、自分と自分の配下以外のタスク
- 1 つの最上位タスクの配下は 200 件まで

#### `teams/{teamId}/taskItemEvents/{eventId}`（新規）

変更の記録。タスクを削除しても記録が残るよう、タスクの配下ではなくチーム直下に置く。

| フィールド         | 型                                     | 用途                                                                                                                                                                              |
| ------------------ | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `itemId`           | string                                 | 対象のタスク                                                                                                                                                                      |
| `rootId`           | string                                 | 対象の最上位タスク。親単位でまとめて読むために使う                                                                                                                                |
| `type`             | string                                 | `item.created` / `item.title_changed` / `item.status_changed` / `item.assignee_changed` / `item.dates_changed` / `item.category_changed` / `item.parent_changed` / `item.removed` |
| `before` / `after` | unknown                                | 変更前後。配下に及ぶ操作では、`after` に配下の件数を入れる                                                                                                                        |
| `actorId`          | string \| null                         | 操作者の UID                                                                                                                                                                      |
| `source`           | `web` \| `discord` \| `system` \| `ai` | β では `web` のみ                                                                                                                                                                 |
| `createdAt`        | timestamp                              |                                                                                                                                                                                   |

追記のみ。説明の変更は記録しない（仮決定 30）。記録する件数は次のとおり。

- 1 件のタスクへの操作: 1 件
- 配下に及ぶ操作（状態の変更・削除・付け替え）: 操作した対象の 1 件
- 祖先が自動で広がったとき: 広がった祖先 1 件ごとに `item.dates_changed` を 1 件
- 進め方からの生成: 親の `item.created` の 1 件（`after` に子の件数）

#### `StepDef`（進め方の工程定義。既存に追加）

| フィールド          | 型                     | 用途                                                          |
| ------------------- | ---------------------- | ------------------------------------------------------------- |
| `durationDays`      | number（任意、1〜365） | 所要日数。生成する子の開始日時を決める。未設定は 1 として扱う |
| `defaultCategoryId` | string \| null（任意） | 生成する子のカテゴリ                                          |

既存の進め方は書き換えない。生成時に存在しないカテゴリは null にする。

#### 既存データの移行

不要（β は新しいコレクションだけを使う）。

### アクセス制御

書き込みはメンバーだけができる。スタッフは閲覧のみ。現行のカンバンのタスク（TE-021）と同じ権限である。

| 操作                                                               | できる人     |
| ------------------------------------------------------------------ | ------------ |
| 閲覧（ガント、タスク詳細、変更の記録）                             | 所属者全員   |
| 作成（子タスクの追加、進め方からの生成を含む）                     | メンバーのみ |
| 編集（タイトル・日時・担当者・カテゴリ・説明・状態・親の付け替え） | メンバーのみ |
| 削除                                                               | メンバーのみ |

作成者や担当者による例外はない。スタッフは、自分が担当者のタスクでも状態を変えられない。

操作層（クライアント）と `firestore.rules` の両方で確認する。rules は既存の関数だけで書ける。

| パス                       | 読み取り       | 作成                                | 更新                                     | 削除           |
| -------------------------- | -------------- | ----------------------------------- | ---------------------------------------- | -------------- |
| `taskItems/{itemId}`       | `isTeamMember` | `isMemberRole` かつ `createdByIsMe` | `isMemberRole` かつ `createdByUnchanged` | `isMemberRole` |
| `taskItemEvents/{eventId}` | `isTeamMember` | `isMemberRole`                      | 不可                                     | 不可           |

配下に及ぶ操作は最大で 200 件余りを 1 回の `writeBatch` で書く。rules が 1 回の書き込みで読める文書数の上限に収まることを、PR A で Emulator を使って確認する。

#### 現行のブリーフ・工程との違い

現行のブリーフ・工程では、スタッフは次の 3 つができる（TE-005、`team/model.md` の「権限」の表）。新タスクではどれもできない。

- ブリーフ（親タスク）の作成
- 自分が作成したブリーフの編集
- 自分が担当する工程の完了・状態の変更

β の間は現行の `/briefs` が残るので、スタッフは従来どおりブリーフを使える。ブリーフを新タスクへ置き換える時点で、次を決める（置き換えの Issue）。

- TE-005 と「権限」の表のうち、スタッフのブリーフ・工程の権限をどう改めるか
- Discord の工程ボタン（現行はロールを問わず完了にできる）を、置き換え後も同じ扱いにするか

### インデックス

`firestore.indexes.json` に追加する。

| コレクション     | フィールド                      | 使うクエリ                                                                       |
| ---------------- | ------------------------------- | -------------------------------------------------------------------------------- |
| `taskItems`      | `startAt` 昇順、`dueAt` 昇順    | 表示範囲と交わるタスク（`startAt <= 範囲の終わり` かつ `dueAt >= 範囲の始まり`） |
| `taskItemEvents` | `itemId` 昇順、`createdAt` 降順 | タスク詳細の変更の記録                                                           |

2 フィールドの不等号を 1 クエリで使えることを、実装の最初に Emulator で確認する。使えない場合は `dueAt >= 範囲の始まり` だけをクエリにし、`startAt` の条件は画面側で絞る。

次のクエリは単一フィールドの自動索引で足りる。

- 日時がないタスク: `dueAt == null`
- 配下の取得: `ancestorIds array-contains`
- 直下の子の取得（タスク詳細の子タスクの一覧、子の `order` の決定）: `parentId ==`
- カテゴリ削除・状態削除・退出時の対象: `categoryId ==` / `columnId ==` / `assigneeId ==`

### 処理の流れ

すべての書き込みは新しい操作層（`src/lib/taskItems/operations`）を通す。1 操作は「権限判定 → 読み込み → 計画 → 変更の記録 → commit」の順で、1 つの `writeBatch` にまとめる。commit が失敗したら何も保存せず、画面にエラーを表示する。値が変わらない操作は commit しない。

1. **作成**: 状態は `TaskStatus` の先頭（`order` 最小）、子の `order` は兄弟（`parentId` が同じタスク）の最大値 + 1（兄弟がいなければ 0）。最上位は作成日の古い順で並べ `order` を使わないので、0 を入れる。親を指定した場合は `ancestorIds` を親から作る。日時を入れた場合は、2 と同じ補完・検証・祖先を広げる処理（確認ダイアログを含む）を行う。最上位の配下が 200 件を超える場合は保存しない
2. **日時の変更**
   1. 片方だけ入力された場合は、もう片方を同じ日で補完する
   2. `startAt > dueAt` なら保存しない
   3. 子を持つタスクを、日時を持つ子より狭い範囲にする変更と、日時を持つ子がいるタスクの日時を空にする変更は保存しない
   4. 変更後の範囲が親からはみ出す場合、はみ出した側だけ親を広げる。親が日時を持たない場合は、親に変更後の範囲と同じ日時を入れる（仮決定 11）。さらに上の祖先についても、最上位まで同じ処理を繰り返す
   5. 祖先の日時が変わる場合は、保存前に確認ダイアログを出す。ダイアログには直近の親の変更前後を出す。親が日時を持たなかった場合、変更元は「未設定」と出す。キャンセルなら何も保存しない
   6. タスクと、日時が変わった祖先を同じ `writeBatch` で更新する
3. **状態の変更**: 対象と配下全員の `columnId` を同じ `writeBatch` で更新する
4. **親の付け替え**: 対象と配下全員の `parentId` / `ancestorIds` を更新する。`order` は付け替え先の兄弟の最大値 + 1。「親なし」を選ぶと最上位になり、`order` は 0 になる。新しい親からはみ出す場合は 2-4 と同じく広げる。付け替え後の最上位の配下が 200 件を超える場合は保存しない
5. **削除**: 対象と配下を同じ `writeBatch` で削除する
6. **進め方から生成**
   1. 入力は、親のタイトル・親の締切（必須）・進め方。工程が 0 件の進め方は選べない
   2. 進め方の `leadDays` の最小値を `m` とする。各子の締切は「親の締切の日 −（`leadDays` − `m`）日」の 23:59:59
   3. 各子の開始は「締切の日 −（`durationDays` − 1）日」の 00:00:00
   4. 子の担当は `defaultAssigneeId`（所属者でなければ null）、カテゴリは `defaultCategoryId`（存在しないカテゴリは null）、`order` は進め方の順。親と子の状態は、作成と同じく `TaskStatus` の先頭
   5. 親の開始は子の開始の最小値、親の締切は入力値
   6. 親と子を同じ `writeBatch` で作成する
7. **カテゴリの削除**: 既存の `deleteCategory` に、そのカテゴリの `taskItems` の `categoryId` を null にする処理を足す
8. **状態の削除**: 既存の `deleteColumn` に、その状態の `taskItems` を既存のタスクと同じ移行先の状態へ移す処理を足す
9. **退出・Kick・アカウント削除**: 既存の Functions（`removeTeamMember` / `leaveTeam` / `leaveSpecificTeam` / `deleteAccount`）に、その所属者が担当者の `taskItems` の `assigneeId` を null にする処理を足す。既存の `tasks` と同じトランザクションで行い、対象の読み取りはトランザクション内のすべての書き込みより前に置く。`leaveTeam` / `leaveSpecificTeam` は、現状ではトランザクションの読み取り順の不具合で退出自体が失敗する（#236）。この 2 つへの追加と確認は #236 の修正後に行う

7 と 8 は、対象の `taskItems` をクエリで集める（既存の `deleteColumn` は対象の ID を画面から受け取るが、新タスクは画面に全件がないため）。対象が 1 回の `writeBatch`（500 書き込み）に収まらない場合は、`taskItems` の更新を先に分割して commit し、最後にカテゴリ・状態の本体を削除する。途中で失敗した場合は本体が残るので、もう一度削除を実行すれば続きから処理される。変更の記録は残さない。

### ガント画面

- ルートは `/gantt`。サイドバー「メイン」に「ガントチャート(β)」を追加する
- PC
  - 左にタスクの列（タイトル・状態・開始日・締切、担当者のアバター、カテゴリのアイコン）。状態は状態名を出し、アイコンがあれば併記する。右に日単位の時間軸を置く
  - 行は最上位のタスクと、その下に `order` 順の子。親の行で開閉できる
  - バーは `startAt` の日から `dueAt` の日まで。色は `TaskStatus.color`。日時がないタスクは行だけ出し、バーを描かない
  - 今日の位置に縦線を引く
  - 列見出しのクリックで昇順、もう一度で降順に並び替える。状態での並び替えは `TaskStatus.order` の順。日時がないタスクは、開始日・締切の並び替えでは昇順・降順とも末尾に置く
- モバイル（`md` 未満）
  - 縦が日付、横がタスク。タスク 1 件が 1 列になり、バーは縦に伸びる
  - 親の列の右に子の列を並べる。親の見出しのタップで子の列を開閉する
  - 列の見出しに、タイトルと状態名を出す。状態にアイコンがあれば併記する（仮決定 32）
- 読み込み
  - 初回は当日の前後 1 か月。時間軸の端まで来たら、その方向に 1 か月広げる
  - 購読は 2 本。読み込み済みの範囲と交わるタスク（範囲が広がるたびに張り替える）と、日時がないタスク全件
  - 日時のない子は、日時を持つ祖先がまだ読み込まれていない間は表示しない。範囲が広がって祖先が読み込まれた時点で、祖先の下に出る（仮決定 31）
- 検索は読み込み済みのデータを画面側で絞る
- 行（モバイルでは列の見出し）のクリックでタスク詳細ドロワーを開く
- `/gantt?item={id}` を直接開いた場合は、そのタスクを ID で 1 件取得してドロワーを開く。存在しないか読めない場合は「タスクが見つかりません」を表示する
- 「タスクを追加」から、単発タスクの作成と、進め方からの生成を選べる。スタッフには「タスクを追加」を出さない
- アクセシビリティ（NFR-009）
  - 行の移動、親の開閉、タスク詳細を開く操作を、キーボードだけで行える
  - 状態は色だけで伝えない。PC は左の列に、モバイルは列の見出しに状態名を出す。バーには「タイトル、状態名、開始〜締切」を読み上げ用の名前として付ける

### タスク詳細ドロワー

タイトル、状態、カテゴリ、担当者、開始・締切（終日ボタン付き）、説明、親タスク（付け替え）、子タスクの一覧と追加、変更の記録、削除。子タスクの一覧は、ドロワーを開いている間、直下の子を `parentId` で購読して `order` 順に出す（ガントの読み込み範囲に依らない）。

スタッフには、編集の入力欄、子タスクの追加、付け替え、削除のボタンを出さず、内容の表示だけにする。

## 制約・注意

- 日時は JST 基準で計算し、演算は `date-fns` を使う（NFR-010）
- 本番反映時に、rules・索引のデプロイと Functions の再デプロイが要る
- 操作は読み込んでから `writeBatch` で保存するので、2 人が同じ親子を同時に操作すると、後から保存した内容で上書きされる（仮決定 33）
- 1 回の `writeBatch` は 500 書き込み以内に収める。配下の上限 200 件は、対象と配下の更新・祖先の更新・変更の記録を 1 回に収めるための値
- 日時がないタスクは全件を購読する。件数が増えて表示が遅くなった場合は、完了のタスクを除くなどの絞り込みを検討する
- β の新タスクは Discord に連携せず、締切のリマインドも届かない。画面上で β であることを示す
- LIGHT プランの月次のタスク作成数に、β の新タスクは数えない（仮決定 17）
- カレンダーは終日の終わりを翌日 00:00:00（排他）で持ち、タスクは 23:59:59 で持つ。揃える修正は別 Issue

## ユーザーへの質問

根拠は Issue #211 のコメント（1 周目と、3〜6 周目のまとめ）。仮決定一覧のうち、特に確認したいものを挙げる。

1. **置き換え後の権限。** 新タスクはメンバーだけが書き込める（決定済み）。現行のブリーフでスタッフができる 3 つの操作（ブリーフの作成、自作のブリーフの編集、担当する工程の完了）と、Discord の工程ボタンをどうするかは、置き換えの Issue で決める。β の間は現行の `/briefs` が残るので影響はない
2. **日時のない親（仮決定 11・29）。** 日時のない親の子に日時を入れると、親にも同じ範囲が入る。日時を持つ子がいる親の日時は空にできない
3. **日時がないタスクの見せ方（仮決定 8）。** 以前の案は「ガントに出さず一覧にだけ出す」だったが、β には一覧画面がない。ガントに行だけ出す案にした
4. **親の状態変更の範囲（仮決定 10）。** 親を「作業中」に変えると、完了済みの子も「作業中」に戻る。完了にしたときだけ子へ反映する案もある
5. **プラン制限（仮決定 17）。** β の間、LIGHT の「タスク作成は当月 5 件」に新タスクを数えない。その間、LIGHT のユーザーはガントからなら制限なくタスクを作れる。数える場合は、作成を Functions 経由にする必要がある
6. **退出時の担当者（仮決定 25）。** β でも Functions を直す。その分、本番反映時に Functions の再デプロイが要る
7. **コメント（仮決定 26）。** β の新タスクにはコメント機能を付けない
8. **Discord・リマインド（仮決定 24）。** β の新タスクは Discord に連携しない
9. **配下の件数の上限（仮決定 15）とコレクション名（仮決定 1）。** 200 件、`taskItems` でよいか
10. **親が読み込まれていない子（仮決定 31）。** 日時のない子は、日時を持つ親が表示範囲に入るまでガントに出ない
