# 対応不可時間（メンバー別の対応不可確認画面） 変更仕様

**作成日**: 2026-11-18
**状態**: 実装中（Issue #210。#204 から分離。進行は「PR 分割と状態」を参照）
**正本**: [docs/仕様・計画/unavailability/](../仕様・計画/unavailability/README.md)（機能識別 ID `UN`）

## 背景・目的

チームで集まれる日を決めるとき、誰がいつ対応できないかを個別に聞いて回っている。メンバーが「この日・この時間帯は対応不可」を自分で申告し、チーム全員が一覧で見られる画面を作る。

当初は「対応可能」を入力する案だったが、入力量が多く続かないため、**空白＝対応可能、入力するのは不可の時間帯だけ**に変更した（2026-11-16）。

## 全体方針

- **入力するのは不可だけ。** 入力のない時間帯は対応可能とみなす
- **予定の中身は持たない。** 保存するのは不可かどうかと、補足用のメモだけ
- **申告の管理はしない。** 催促・リマインドは作らず、代わりに「最終更新 / 未入力」を見せて誤読を防ぐ
- **本人だけが書く。** `rom` も自分の分は入力できる。代理入力は持たない
- **既存機能に触らない。** チーム予定・カレンダー部品・Google カレンダー書き出しとは独立した追加機能とする
- **仕様の詳細は正本に書く。** 本書は経緯・実装の分割・進行状況を管理し、要件・モデル・フローは正本を参照する

## 決定事項の要約

詳細は正本の [requirements](../仕様・計画/unavailability/requirements.md) / [model](../仕様・計画/unavailability/model.md) / [flows](../仕様・計画/unavailability/flows.md) を参照する。

| 項目 | 決定 |
| --- | --- |
| 粒度 | 日付 + 1 時間単位。1 日に複数区間。日またぎは保存時に日付ごとに分割（終了は排他的境界） |
| 保存・表示期間 | 前月 1 日〜翌月末日。翌月末日より先は入力不可。前々月以前は毎月 1 日 0:00 JST に削除 |
| 権限 | 書き込みは本人のみ（`rom` 含む）。閲覧はチーム全メンバー |
| データ配置 | `teams/{teamId}/unavailability/{userId}_{yyyy-mm}`。日ごとに 24 ビットの整数マスク、メモは別配列 |
| 保存経路 | クライアントから Firestore へ直接書く。ルールは本人性・ドキュメント ID・フィールド名・メモ件数を強制し、値の検証は Zod で行う |
| メモ | 任意の時間帯に付けられる。同一日内・1 時間単位、100 字、1 ヶ月 200 件。本人のみ編集・削除 |
| 一覧 | 行＝メンバー、列＝日。× と日ごとの不可人数、最終更新。自分の行を最上段に固定 |
| メンバー詳細 | 縦の時間軸に不可とメモ。「日単位で表示」の切り替え。他人の詳細は閲覧のみ |
| 入力 | ドラッグ塗り（第 1 弾）、CSV・定期入力（第 2 弾。「展開 → プレビュー → 和集合で保存」の共通経路） |
| 置き場所 | `/unavailability`。サイドバー「メイン」の「スケジュール」直下、モバイルは「その他」ドロワー |
| プラン | 制限なし（plan の正本に書く。本カテゴリの正本には書かない） |

## Issue から補った点

Issue #210 の本文に無い、または曖昧だった点を設計時に次のとおり決めた。レビューで覆す場合は正本と本書を直す。

| # | 項目 | 決定 | 理由 |
| --- | --- | --- | --- |
| 1 | メモの形 | `{ id, date, start, end, text }`（`start` / `end` は時の整数） | Issue の `{ start, end, text }` では日付と編集・削除の対象を特定できない（2026-11-18 確認済み） |
| 2 | 保存経路 | クライアント直書き + Zod。読み取り側も Zod で不正値を捨てる | ルールは map・配列の中身を走査できない。不正値を入れられるのは本人のドキュメントだけ（2026-11-18 確認済み） |
| 3 | 機能識別 ID | `UN` | `user` の `US` と重ならない 2 文字 |
| 4 | ナビの表示名 | 「対応不可時間」 | 文言統一（「対応不可」）に合わせた |
| 5 | 過去日の入力 | 表示範囲内（前月 1 日以降）なら過去も編集できる | 入れ忘れの訂正を妨げる理由がない。範囲の判定が 1 つで済む |
| 6 | メンバー詳細の先頭行 | クリックした日が当日なら現在時刻、それ以外はその日の 0:00 | Issue は「開いた時点の現在時刻」だが、別の日のセルを押して当日が開くのを避ける（2026-11-18 確認済み） |
| 7 | 塗りと消し | ドラッグの始点が空なら塗る、不可なら消す。「保存」で確定 | 消す操作が Issue に無い。E2E ③（塗って保存）に合わせた |
| 8 | 不可人数・時間帯フィルタの母数 | メンバーで絞り込んだ後の、表示中のメンバー | 「この人たちで集まれる日」を探す用途に合う |
| 9 | 最終更新の算出 | 読み込み済み月ドキュメントの `updatedAt` の最新。1 つも無ければ「未入力」 | 追加フィールド・追加クエリが要らない。前月・翌月を読み込むと表示が変わりうる |
| 10 | CSV の日またぎ | `end` が `start` より前なら翌日へまたぐ。同値は不正 | 入力全般の「日をまたいでよい」に合わせた |
| 11 | CSV の範囲外の日付 | 不正にせず、プレビューで切り捨て件数を出す | 定期入力と同じ経路・同じ扱いにする |
| 12 | CSV・定期入力とメモ | 対象外（不可時間だけを作る） | 形式が `date,start,end` の 1 種類のため |
| 13 | 退出時の削除の失敗 | 退出等は成立させ、エラーログに残す。残りは月次削除で消える | 掃除の失敗で退出を止めない。失敗は隠さない |
| 14 | クライアントからの削除 | 不可（月ドキュメントの削除は Admin SDK のみ） | 不可をすべて消した月も `updatedAt` を残し「入力済み」と区別する |
| 15 | メモの保存 | 追加・編集・削除はブラウザ内に保持し、「保存」で不可時間とまとめて月ドキュメントごとに 1 回書く | メモを続けて追記しても、件数ぶんの読み書きが発生しない（PR #223 のレビューで決定） |
| 16 | 未保存のまま閉じる | 確認を出す（編集に戻る / 破棄して閉じる）。リロード・タブを閉じる操作にはブラウザの離脱確認を出す | 入力した内容を黙って失わせない |
| 17 | 未保存中に届いた更新 | 購読データの上に未保存の変更（変更した日・メモの差分）を重ねて表示する | 別の端末やメンバーの保存で、入力中の内容が消えないようにする |
| 18 | タッチ端末の入力 | 対応不可の列の上のドラッグだけを塗りに使い、縦スクロールは日時の列・メモ欄で行う | 塗りと縦スクロールを同じ指の動きで両立できないため、場所で分ける |
| 19 | 未保存の見せ方 | 塗り・消し・メモとも破線で表示し、「未保存の変更があります」を「保存」の横に出す | 保存し忘れに気づけるようにする |

## 各 PR の作業内容

### PR A: 土台

- 型 `UnavailabilityMonth` / `UnavailabilityNote`（`src/types/unavailability.ts`）と Zod スキーマ（`src/lib/validations/unavailability.ts`）
- 純関数（`src/lib/unavailability/`）: 時間範囲 ⇄ 日マスク、日またぎ・月またぎの分割、OR 追記、ビット数、時間帯マスクとの AND、保存範囲（前月 1 日〜翌月末日）の判定
- リポジトリ（`src/lib/repositories/unavailability.ts`）: 月の購読と、1 ヶ月分の保存（変更した日とメモをまとめて 1 回で書く）

- 正本の同期: team/flows（退出・Kick）、user/flows（アカウント削除）、plan/requirements（PL-002 に「対応不可時間の入力は無制限」を追記）

## E2E

Emulator のシードに対応不可データを追加して行う。

1. 一覧が開き、自分の行が最上段にある
2. セルをクリックするとメンバー詳細が開き、シードした不可時間帯が赤く出る
3. 自分の詳細で塗って保存すると、一覧の × と最終更新が更新される
4. メモを追加・削除して保存できる。他人の詳細ではメモの追加ボタンが出ない

## 本番反映時の注意

- 本 PR のマージ後、`firebase deploy --only firestore`（rules + indexes）と Functions の再デプロイが必要。ルールが未デプロイだと画面は全メンバーが permission-denied になる
- 月次削除はコレクショングループのインデックスが無いと失敗する。初回実行（翌月 1 日）までにインデックスが有効になっていることを確認する
