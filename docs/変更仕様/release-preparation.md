## T4: 課金方式の実装

### 内容

PARTY プラン（有料）の課金手段を実装する。現状は `NEXT_PUBLIC_PARTY_SIGNUP_URL`（外部フォーム想定）への遷移のみで、`users/{uid}.plan` を書き換えるバックエンドが存在しない（`onUserCreate` で全員 `light` 固定）。

### 実装方針（2026-07-17 ユーザー決定済み）

**Stripe Checkout + Customer Portal 方式で確定。** あわせて以下も決定済み:

- **課金単位**: ユーザー単位 月額500円（税込）で確定（PL-004/005・LP・法務ページの現行記載どおり）
- **無料トライアル**: 正式課金開始時に Stripe の `trial_period_days`（14日）で提供する。試用モード期間中の LP は「公開試用期間につき全機能無料」の告知に差し替え済み
- **試用モードの終了**: T4 完了・課金導線の公開と同時に `FREE_PARTY_MODE` を無効化する

実装内容:

- Cloud Functions に Checkout セッション作成 API と Stripe Webhook 受信 API を追加。
- `checkout.session.completed` / `customer.subscription.deleted` 等の Webhook で `users/{uid}.plan` を `party` / `light` に更新する（`teams/*/members/*.plan` への伝播も含む）。

- プラン判定は既存の `plan` フィールド＋T5 の共通判定関数のまま変更不要。
- プラン変更時の権限チェック・値の強制は**サーバーサイド（Cloud Functions）で行う**（NFR-006 / PL-009 準拠）。
- 確定した仕様は `docs/仕様・計画/plan/`（PL-008 ほか）へ反映する。

### 要件（実装のゴール）

- ユーザーが自力で PARTY プランへ加入・解約でき、`plan` フィールドが正しく遷移すること（案 A の場合）。

## T5: 試用期間の全員 PARTY プラン化

### 内容

動作テスト・公開試用のあいだ、課金しなくても全ユーザーを PARTY プラン相当として扱う。

### 実装方針

- **ユーザーデータ（`users/{uid}.plan`）は書き換えない。** 試用終了後に個別ロールバックが必要になるため。
- 代わりに**プラン判定ロジックを一元化し、そこにフラグを差し込む**:
  1. `isPartyPlan(user)` 相当の共通判定関数を `src/` と `functions/src/` の双方（または共有モジュール）に用意し、散在する `plan !== 'party'` / `plan: 'light'` 判定を置き換える。
  2. 環境変数 `FREE_PARTY_MODE`（クライアント側は `NEXT_PUBLIC_FREE_PARTY_MODE`）が有効な場合、判定関数が常に `party` を返す。
  3. バナー広告・月次上限・3 名以上チーム参加制限（PL-005）・通知制限が一括で PARTY 挙動になることを確認する。
- 試用終了時は環境変数を無効化するだけで LIGHT 制限へ戻る。

### 要件（実装のゴール）

- フラグ ON で全ユーザーが PARTY 相当（広告非表示・上限なし）になり、OFF に戻すとデータ変更なしで LIGHT 制限が復活すること。
- フラグの強制はサーバーサイドの判定にも適用されること（クライアントのみの制御にしない）。

## T6: アプリ内広告の実装（→ 自社告知枠方式に変更）

### 内容

LIGHT プランユーザー向けの広告・告知枠（PL-002）を実装する。現状 `src/components/plan/BannerAd.tsx` は点線枠のプレースホルダーで、ダッシュボードにのみ配置されている。

**方針変更（2026-07-17 決定）**: 外部広告ネットワーク（AdSense）は当面見送り、**自社告知枠**として実装する。

- 見送り理由: ①公開コンテンツが LP＋法務ページのみで、ツール系サイトは「有用性の低いコンテンツ」判定により審査通過が困難 ②ログイン内配信はクローラー用アカウント提供等の追加運用が必要 ③想定ユーザー規模では広告収益が月数百円未満で、審査・CMP・品質管理のコストに見合わない
- 再挑戦の条件（バックログ）: MAU が数百人規模に成長し、集客用の公開コンテンツ（使い方ガイド・配信者向け記事 8〜10 本以上）を持つ段階で AdSense を再検討する

### 実装方針

1. **自社告知枠**: `BannerAd` を自社コンテンツのローテーション表示に差し替える（第一弾は PARTY プランへのアップグレード訴求。将来は新機能告知・お知らせにも利用可）。
2. **表示条件**: プラン判定は T5 の共通判定関数（`isPartyPlan`）を使用し、PARTY（および FREE_PARTY_MODE 中）は非表示。LIGHT の差別化要素としての位置づけ（PL-002）は維持する。
3. **配置**: コンテンツ閲覧を妨げない位置とし、対象画面（ダッシュボード以外に追加するか）を確定する。枠サイズは固定し CLS を発生させない。
4. **外部スクリプト不要**: AdSense を使わないため、同意管理（CMP）や広告向けポリシー追記は不要。T3 で追加済みの予告条項（「広告配信を利用する場合があります」）は将来の再挑戦に備えて残置する。

### 要件（実装のゴール）

- LIGHT ユーザーにのみ自社告知枠が表示され、PARTY ユーザー（および試用モード中）には表示されないこと。
- 告知枠のデザインがアプリのデザインシステムに準拠し、CLS を発生させないこと。

## T8: レスポンシブデザインの最適化

### 内容

モバイル表示への不満が多いため、レスポンシブ対応を全画面で見直す。

### 聞き取り結果（2026-07-17 実施）

- **不満が大きい画面**: スケジュール（カレンダー）とコラボ調整の2画面
- **症状**: 全類型に該当 — ①レイアウト崩れ・はみ出し ②タップ・ドラッグがしにくい ③情報が見切れる・狭い ④操作動線が深い
- **利用環境**: スマホ縦持ち（幅〜430px）が主
- **優先順位**: ①スケジュール（カレンダー）が最優先 → ②コラボ調整 → ③その他画面は監査で拾った分を対応

### 実装方針

1. **監査**: 着手時にまず 375px でスケジュール画面（週/月カレンダー・スケジュールモーダル）とコラボ調整（候補日マトリクス・回答画面）をシードデータ入りで実機確認し、上記4症状に対応する具体的な修正項目リストを作る。その後 375px / 768px / 1280px の 3 幅で全画面を確認し、崩れ・操作困難箇所を一覧化する。
2. **方針**:
   - ブレークポイントは既存の `md`（768px）基準を維持し、画面ごとの独自ブレークポイントを排除する。
   - タップターゲットは 44px 以上を確保する。
   - スマホ縦持ちを第一級の利用環境として扱う（症状④に対し、カレンダーの予定確認・登録とコラボ回答の主要動線はタップ数の削減も検討する）。
   - PC/モバイルで DOM を二重マウントしている箇所は `useMediaQuery` による片側マウントへ寄せる（`ui-performance-optimization.md` 変更 2 と同方針）。
3. T7 のデザイン統一と画面単位でまとめて実施してよい。

### 要件（実装のゴール）

- スマホ縦持ち（375px）でスケジュール・コラボ調整の主要操作（予定確認・登録・候補日回答・確定）が快適に完了できること。
- 優先順位上位の不満点がすべて解消され、3 幅すべてで横スクロール・レイアウト崩れがないこと。

## T11: クローズドベータ入場制限（2026-07-17 追加・方式決定済み）

### 内容

課金開始（正式リリース）までは、招待したテスターのみがアプリを利用できるようにする。現状は誰でもサインイン→`onUserCreate` でソロチームまで自動生成されるため、入場を止める仕組みがない。

**決定方式**: アプリ層ゲート＋利用申請フロー（Identity Platform へのアップグレードは行わない。ブロッキング関数方式は見送り）。

### 実装方針

1. **許可リスト**: Firestore ルートコレクション `beta_allowlist/{email}`（ドキュメントID = 小文字正規化したメールアドレス）。**メールアドレスはソースコード・リポジトリに一切記録しない**。
   - ルール: `list` は全面拒否。`get` は認証済みユーザーが自分のメール（`request.auth.token.email`）と一致する ID のみ許可（列挙・推測確認を防止）
   - メール/パスワード認証ユーザーは `email_verified == true` を条件に含める（Google ログインは常に verified）
2. **ゲートフラグ**: Firestore `app_config/beta { enabled: boolean }` を正とし、Firestore ルールは `get()` でこのドキュメントを参照して「ベータ無効 or allowlist 在籍」を主要コレクションのアクセス条件に追加する（ルールは環境変数を参照できないため）。クライアントの表示切替用に `NEXT_PUBLIC_CLOSED_BETA` も併用する
3. **待機画面**: allowlist 外のユーザーはログイン後「正式公開までお待ちください」画面のみ表示（サインアウトと利用申請ボタンのみ）
4. **利用申請フロー**: 申請ボタン → callable Function が `beta_requests` に記録し、既存の問い合わせメール基盤（Gmail SMTP + nodemailer、Secrets `GMAIL_USER`/`GMAIL_APP_PASSWORD` を再利用）で管理者へ通知メールを送信。管理者はコンソールで `beta_allowlist` へ昇格させる
5. **管理スクリプト**: `scripts/beta-allowlist.mjs`（add / remove / list。メールは実行時引数で渡す）
6. **解除（課金開始時）**: `app_config/beta.enabled = false` ＋ env フラグ削除で全ユーザー即開放。待機中に作成されたアカウント・ソロチームはそのまま正式利用に移行する

### 要件（実装のゴール）

- allowlist 外のユーザーはログインしても待機画面のみで、Firestore データへのアクセスがルールで拒否されること（クライアント制御だけにしない）
- 申請時に管理者へメールが届き、コンソール登録後の次回アクセスで利用開始できること
- フラグ OFF で全ユーザーが即時開放され、コード変更・データ移行が不要なこと
