# タスク管理 v2（1枚紙）・AI 刷新・Discord 連携強化 変更仕様

**作成日**: 2026-09-06
**状態**: 確定（2026-09-06 ユーザーレビュー済み。全体像・法務方針は承認。実装は「第 1 弾の実装タスク」から着手）

## 背景・目的

RisukeruGG は現状、スケジュール・カンバン・コラボ調整・Discord 通知・AI チャットがそれぞれ既存ツールの代替として並んでいるだけで、連携によるメリットが生まれていない。運営チームでの実利用（2026-08 時点）から以下が判明した。

- Discord に流れるメッセージは**タスクの完了報告がほぼすべて**。相談や「AI に登録して」という依頼は発生しなかった
- 担当者の声: 「AI にプロンプトを打つくらいなら直接入力する方が早い」
- RisukeruGG に入力しているのは編集担当のみ。オペレーターや出演者は触っていない
- 進捗の把握・締切の記憶といった業務管理が人の裁量に任されている。**「忘れる仕事をアプリが引き受ける」**ことが本製品の本質だが、実現できていない

原因は機能の不足ではなく、製品の中心に置いているものの選択にある。

1. **単位が「タスク」であって「動画1本」ではない。** 動画制作は1本ごとに少数の異質な工程が順番と依存を持って進む。独立した同質のタスクを流すカンバンはこの形を表現できず、「次に誰の手に渡るか」「この工程に何が必要か」が人の記憶に残る
2. **Discord 連携が通知の出口で止まっている。** Discord 上の「終わったよ」は RisukeruGG に戻らず、Discord ユーザーと RisukeruGG ユーザーも紐づいていない（現行 IN-015）。結果「結局 Discord でいい」になる
3. **AI が「行き先」になっている。** `/chat` に行って話しかける設計は、日常入力としては直接入力に負ける。AI が価値を出せるのは、対話で運用を引き出す入口と、運用を観察して提案する出口の両端に限られる

本書は次の 3 本柱を 1 つの変更として定義する。

| 柱 | 内容 | 位置づけ |
| --- | --- | --- |
| **A. タスク管理 v2（1枚紙）** | 動画1本を「ブリーフ（1枚紙）」として起こし、工程を回しながら差分で進める新方式。既存カンバンは残し、新メニューとして並行提供する | 製品の新しい中心 |
| **B. Discord 連携強化** | Discord 名によるメンション、ブリーフごとのスレッド、ボタン完了、朝ダイジェスト、締切前メンション。Discord を「入口の一つ」にする | **最重要** |
| **C. AI 機能の刷新** | AI にできることを能力単位で定義・管理し、プロンプトをバージョン管理する。対話による「進め方」の引き出しと、運用からの学習提案を担わせる | A・B を支える基盤 |
| **D. 操作層の一本化と公開 API・MCP 対応** | Web・Discord・AI が共有する操作層を定義し、同じ操作を公開 API として提供する。将来の MCP サーバーはその薄い皮として実装する | A〜C の設計制約。実装は後段 |

## 全体方針（設計原則）

- **状態は一つ、入口は二つ。** ブリーフの状態は Firestore に一つだけ持ち、Web と Discord のどちらで変えても両方に反映する。Web は俯瞰と一括調整、Discord は流れの中での報告と確認を担う
- **日常操作にプロンプトを書かせない。** 完了報告はボタン。締切逆算・催促・ダイジェストは決定的（AI なし）に動く
- **AI が覚えるものは文章ではなく構造化データ。** 「チームの進め方」は工程・担当・順序・必要情報・日数として保存し、Web で見て直せる。プロンプトに蓄積しない
- **提案は人が承認する。** AI の出力はすべて提案として保存し、承認後にのみ状態へ反映する（既存の `%%PROPOSAL%%` → Zod 再検証 → 登録の流儀を踏襲）
- **既存機能を壊さない。** カンバン（`/tasks`）、スケジュール、コラボ、既存 AI チャットはそのまま動く。v2 は追加であり置換ではない
- **段階導入。** 各段階の終わりに運営チームで実運用し、「あれどうなった？」と人が聞く回数が減ったかで判断する
- **操作層は一つ。** ブリーフに対する操作（作成・工程完了・締切変更など）は入力スキーマ付きの操作として一か所に定義し、Web の画面・Discord のボタン・AI の tool・公開 API・MCP はすべてその操作を呼ぶ。入口ごとに別の書き込みロジックを持たない

## 用語

| 用語 | 定義 |
| --- | --- |
| **ブリーフ（1枚紙）** | 動画・配信1本を表す親エンティティ。見出し（公開予定日・出演者・概要・リンク）と工程一覧を持つ |

| **AI 能力（capability）** | AI にさせる仕事の単位。入力・出力スキーマ・プロンプトテンプレート・実行面（Web / Discord / バックグラウンド）を持つ |

## A. タスク管理 v2（1枚紙）

### 内容

動画1本を「ブリーフ」として起こし、進め方から工程が埋まった1枚紙を Web 上でメンバー全員が参照・更新できるようにする。カンバンは「全ブリーフの工程を横断で見る」二次ビューとして残す。

### ナビゲーション

- サイドバー「メイン」に **「タスク管理 v2」**（ルート `/briefs`、アイコン `article`）を追加する。既存「タスク管理」（`/tasks`）はそのまま残す
- v2 は当面 β 扱いとし、メニューに β バッジを表示する。プラン制限は既存タスクと同じ扱い（上限は工程数ではなくブリーフ数で数える。値は plan カテゴリで決める）

### モデル

```
teams/{teamId}/playbooks/{playbookId}                 ← 進め方
teams/{teamId}/briefs/{briefId}                       ← ブリーフ
teams/{teamId}/briefs/{briefId}/steps/{stepId}        ← 工程
teams/{teamId}/briefs/{briefId}/steps/{stepId}/comments/{commentId}
teams/{teamId}/briefs/{briefId}/events/{eventId}      ← 差分
```

#### Playbook（進め方）

| フィールド | 型 | 意味 |
| --- | --- | --- |
| `id` | string | ドキュメント ID |
| `name` | string | 例: 「YouTube 動画（編集あり）」「生配信」 |
| `version` | number | 更新のたびに +1。ブリーフは生成時の版を記録する |
| `origin` | `dialogue` \| `manual` \| `derived` | 対話で作成 / 手で作成 / 既存ブリーフから作成 |
| `headerFields` | `FieldDef[]` | 見出しに置く項目の定義（既定: 概要・素材リンク・出演者） |
| `steps` | `StepDef[]` | 工程の型（順序どおり） |
| `createdAt` / `updatedAt` | timestamp | |

`StepDef`:

| フィールド | 型 | 意味 |
| --- | --- | --- |
| `key` | string | 進め方内で一意なキー（学習・差分の突合に使う） |
| `title` | string | 例: 「サムネ作成」 |
| `roleLabel` | string \| null | 例: 「編集」「サムネ」「出演者」。表示と既定担当の推定に使う |
| `defaultAssigneeId` | string \| null | 既定の担当 UID |
| `leadDays` | number | 公開予定日の何日前を締切とするか |
| `dependsOn` | string[] | 先行工程の `key`。空なら最初から着手可能 |
| `requiredFields` | `FieldDef[]` | この工程を始めるのに必要な情報（例: サムネ文言案、素材の場所） |
| `reminderDaysBefore` | number | 締切の何日前にメンションするか（既定 1） |
| `optional` | boolean | 飛ばせる工程か |

`FieldDef`: `{ key, label, type: 'text' | 'url' | 'number' | 'date' | 'select', options?, required, ownerRoleLabel? }`。`ownerRoleLabel` は「この情報を出す人」の役割で、入力待ちの催促先になる。

| `fields` | Record<string, unknown> | 見出し項目の値（`headerFields` に従う） |

| `discord` | `{ threadId, summaryMessageId, channelId } \| null` | B-2 で使用 |
| `createdBy` / `createdAt` / `updatedAt` | | |

#### Step（工程）

| フィールド | 型 | 意味 |
| --- | --- | --- |
| `id` / `key` | string | `key` は StepDef の key（手追加は `custom_*`） |
| `title` | string | |

#### StepComment

工程内のやり取り。`{ id, authorId, body, source: 'web' | 'discord', discordMessageId?, createdAt }`。Discord スレッド内の該当工程への返信は B-2 で取り込む。

#### BriefEvent（差分）

| フィールド | 型 | 意味 |
| --- | --- | --- |
| `type` | string | `brief.publishAt_changed` / `step.status_changed` / `step.assignee_changed` / `step.dueDate_changed` / `step.field_filled` / `step.added` / `step.skipped` など |
| `stepKey` | string \| null | 対象工程 |
| `before` / `after` | unknown | 変更前後 |
| `actorId` | string \| null | 操作者 UID。システム由来・Discord 由来は null |
| `source` | `web` \| `discord` \| `system` \| `ai` | |
| `createdAt` | timestamp | |

### 規則

- **締切の逆算**: `step.dueDate = brief.publishAt − step.leadDays`。`publishAt` 変更時は `dueDateOverridden = false` の工程をすべて再計算し、各工程の変更を差分として記録する。`publishAt` が null なら締切なし
- **状態遷移**: `dependsOn` の工程がすべて `done` または `skipped` になった時点で `waiting → ready`。`ready → in_progress` は任意（着手ボタン）。`ready | in_progress → done`。`optional` の工程のみ `skipped` にできる。`done → ready` の差し戻しは operator / member が可能
- **入力待ち**: `ready` かつ `requiredFields` の `required` 項目が未入力の工程は「入力待ち」として表示し、催促先は `ownerRoleLabel` に一致する担当、なければブリーフ作成者
- **ブリーフの状態**: 全工程が `done | skipped` になったら `published` 候補として表示し、公開日を過ぎたら自動で `published` にする（YouTube 連携は本書のスコープ外）
- **1枚は1枚**: 1枚紙画面の本文には工程の状態・担当・締切のみを表示し、`fields` とコメントは工程パネル（右側ドロワー、モバイルは全画面）で開く

### 画面

1. **ブリーフ一覧（`/briefs`）**: 進行中のブリーフをカード一覧。各カードに公開予定日・進捗の帯（done 数 / 全体）・入力待ちと遅延のバッジ。フィルタ: 自分が担当する工程があるもの
2. **1枚紙（`/briefs/{briefId}`）**: 見出し（公開予定日・出演者・`fields`）と工程一覧。工程行で状態・担当・締切をインライン編集。公開日変更時は再計算される締切を差分プレビューで示してから保存
3. **工程パネル**: `fields` の入力、コメント、完了・着手・飛ばす。Discord スレッドへのリンク
4. **自分の工程（`/briefs/mine`）**: 全ブリーフの自分の担当工程を締切順に一覧。複数動画を抱える編集者向け
5. **進め方設定（`/briefs/playbooks`）**: 進め方の一覧・編集。工程の並べ替え、担当・日数・必要情報の編集。C-3 の提案はここに差分として表示
6. **新規ブリーフ**: タイトル・公開予定日・進め方の選択。進め方が 0 件のときは C-2 の対話、C-2 未実装の間は空の工程一覧から手で追加

### 既存カンバンとの関係

- `/tasks` のタスクと v2 の工程は別コレクションで、相互に移行しない（本書のスコープ外）
- 既存の「タスク詳細から複製」は、v2 では「このブリーフから進め方を作る」（`origin: derived`）として再解釈する
- 列（`TaskStatus`）は v2 では使わない。工程の状態は固定の 5 値

### 権限

| 操作 | operator | member | rom |
| --- | --- | --- | --- |
| ブリーフ・工程の作成・編集・完了 | ○ | ○ | × |
| 進め方の編集 | ○ | ○ | × |
| 進め方の提案の承認 | ○ | × | × |
| 閲覧 | ○ | ○ | ○ |

Firestore ルールで強制する（NFR-006）。

### 要件（実装のゴール）

- 公開予定日を入力するだけで、進め方どおりの工程・担当・締切が埋まった1枚紙が生成される
- 公開予定日を変更すると、手で固定した工程を除く全締切が再計算され、変更内容が差分として残る
- 工程の完了で後続工程が自動的に着手可能になる
- 必要情報が未入力の工程が「入力待ち」として、誰に何が必要かまで表示される
- 既存 `/tasks` の挙動・データに変更がない

## B. Discord 連携強化（最重要）

### 内容

Discord を「通知の出口」から「ブリーフを回す場所の一つ」に変える。人はブリーフ単位のスレッドで報告し、アプリは締切と催促を引き受ける。

### B-1. Discord 名の保持とメンション解決

個人単位の識別が必要な場面は「担当者へのメンション」だけであり、アカウント連携（OAuth）も専用コマンドも設けない。メンバーに Discord のユーザー名を持たせ、送信時に Bot が ID に解決する。

- Discord のメンション記法は `<@ユーザーID>` であり、本文に `@名前` と書いても通知は飛ばない（文字列として表示されるだけ）。そのため名前から ID への解決が必要になるが、Bot トークンで使える「Search Guild Members」（`GET /guilds/{guildId}/members/search?query=名前`）は特権 Intent を必要とせず、これで解決できる
- 保持するのは `TeamMember.discordUsername: string | null`（`teams/{teamId}/members/{uid}`、team カテゴリで正本化）。Discord の**ユーザー名**（`@` の後ろに表示される一意の名前）を入力する。表示名（ニックネーム）は重複しうるため使わない
- 入力は本人が `/settings/profile`（当該チームのメンバー情報）で、またはオペレーターが `/team` のメンバー行で行う。任意で、未入力でも B-2 以降は動く
- 解決の規則: 送信時に `discordUsername` でサーバー内検索し、一致した ID で `<@id>` を生成する。一致した ID は `TeamMember.discordUserId` にキャッシュし、以後は検索を省く。一致しない場合は `displayName` を文字列で表示し、当該メンバーの行に「Discord 名が見つかりません」を Web 側で表示する
- **IN-015 は次のように改める**: 「個人 Discord ユーザーの RisukeruGG アカウントへのログイン連携は行わない。メンション用に `TeamMember.discordUsername` を保持し、送信時にサーバー内検索で解決する」
- ボタンを誰が押したかは記録しない（サーバーに居ることを信頼境界とする。現行 `/risukerugg` と同じ考え方）。Discord 由来の差分は `actorId: null`、`source: 'discord'` とする。ephemeral 応答は使わない（IN-013 維持）
- **取り扱い区分**: Discord のユーザー名・ユーザー ID は、同じサーバーに居る誰もが見られる公開識別子であり、それ単体でログイン・DM・データ取得はできない。機密情報（トークン・口座情報等）には当たらないが、個人を識別する情報ではあるため次を守る。(1) プライバシーポリシー第 2 条「ユーザーが登録・作成する情報」に「Discord ユーザー名・ユーザー ID（任意）」を追記し、利用目的を「Discord 連携経由の通知・メンションの配信」とする。(2) 読み取りは同一チームのメンバーに限定する（`members` サブコレクションの既存ルール）。(3) 本人がいつでも削除でき、アカウント削除時にメンバー情報と共に消える。(4) Discord のトークン類・メッセージ本文は保持しない（Bot トークンは環境変数、Webhook URL は operator 限定という現行の扱いを維持）

### B-2. ブリーフ別スレッドとボタン完了

- `DiscordTeamConfig` に `briefChannelId`（ブリーフ用スレッドの親チャンネル）を追加。未設定時は通知チャンネル `channelId` を使う
- ブリーフ作成時に Bot が親チャンネルに **公開スレッド**（名前: ブリーフのタイトル）を作成し、先頭に**要約メッセージ**を投稿する。要約は「公開予定日 / 工程ごとの状態・担当・締切 / 入力待ち」で、状態が変わるたびに Bot が同じメッセージを編集する（1枚紙の生きた写し）
- Discord はスレッドの入れ子を持たないため、工程ごとのスレッドは作らない。工程のやり取りはブリーフのスレッド内で「【工程名】」を頭に付けた投稿として扱う
- 工程が `ready` になった時点で、スレッドに **着手可能通知**を投稿する: 「【サムネ作成】@担当 着手できます。締切 9/12。必要な情報: 文言案（未入力）」。ボタン: **完了** / **着手** / **Web で開く**（リンク）。`custom_id` は `step_done:{teamId}:{briefId}:{stepId}` の形式
- ボタンはサーバーの誰でも押せる。押下で工程を `done` にし、要約を更新し、後続工程の着手可能通知を投稿する。差分は `source: 'discord'`、`actorId: null`（誰が押したかは記録しない）
- スレッド内の通常メッセージは取り込まない（Message Content Intent 不要）。完了報告はボタンのみで行う
- Web 側の工程パネルにスレッドへのリンクを表示し、Discord の要約メッセージに 1枚紙の URL を載せる
- 既存の Bot 権限に「公開スレッドの作成 / スレッドでのメッセージ送信 / メッセージの管理（自メッセージの編集・ピン留め）」を追加する。**連携済みサーバーは招待 URL の再実行が必要**になるため、設定画面で「権限の更新が必要」を表示する

### B-3. 朝ダイジェストと締切前メンション

- `DiscordTeamConfig` に `digestChannelId`（未設定時は `channelId`）、`digestTime`（既定 `09:00`、JST）、`digestEnabled`（既定 true）を追加
- Cloud Scheduler（毎時実行）で該当時刻のチームに対し、次を 1 投稿にまとめる: **今日が締切の工程 / 締切を過ぎた工程 / 担当未定の工程 / 入力待ちの工程 / 昨日からの差分（公開日変更・完了・担当変更）**。該当なしの項目は省略し、すべて該当なしなら投稿しない
- 各工程の `reminderDaysBefore` に従い、締切 N 日前の朝（ダイジェストと同時刻）にブリーフのスレッドで担当者にメンションする。担当未定なら operator 全員にメンションする
- 締切超過の工程は、ダイジェストで超過日数付きで毎日表示する（エスカレーションはこれで行い、別途 DM はしない）

### 既存の通知トグルとの関係

- 既存 4 トグル（IN-003）はそのまま。ブリーフ関連の投稿はスレッド内で完結するため通知チャンネルには流さない
- `/risukerugg` コマンドと `discord_sessions` は現状維持。C-1 で AI 能力レジストリに載せ替える

### 要件（実装のゴール）

- 編集者は Discord のスレッドでボタンを 1 回押すだけで工程を完了でき、Web を開かずに済む
- オペレーターと出演者は Web を開かなくても、朝のダイジェストとスレッドの要約で進捗と自分宛ての依頼が分かる
- 締切前・締切超過・担当未定・入力待ちの検出と催促を人が行わなくてよい
- 担当者に Discord 名が入っていれば、着手可能通知と締切前リマインドが本人にメンションで届く

## C. AI 機能の刷新

### 内容

「AI にできること」を能力（capability）単位で定義し、プロンプトをコードとしてバージョン管理・回帰テストする。AI の役割を日常入力から、**進め方の引き出し（入口）**と**運用からの学習提案（出口）**に移す。既存の Web チャットと `/risukerugg` は残し、同じ基盤に載せ替える。

### C-1. AI 能力レジストリとプロンプト管理

- `src/lib/ai/capabilities/` に能力ごとのモジュールを置く。各能力は `{ id, description, surfaces, inputSchema, outputSchema, promptTemplate, model }` を持つ
- プロンプトテンプレートは `src/lib/ai/prompts/{capabilityId}.md` に置き、先頭のフロントマターに `version` と `changelog` を持つ。変更は PR レビューを通す
- 各能力に固定入力のフィクスチャと期待出力のスナップショットテスト（`tests/unit/ai/`）を用意し、プロンプト変更の回帰を検出する
- チーム追加指示: `teams/{teamId}/ai/settings = { teamInstructions: string, enabledCapabilities: string[] }`。用語や呼び方などチーム固有の指示を operator が `/settings/ai` で編集し、全能力のプロンプトに共通で注入する
- `/settings/ai` に能力の一覧（説明・実行面・プロンプト版・有効 / 無効）を表示する。「AI に何ができるか」がここで分かる状態にする
- バックグラウンド能力（C-3）は Cloud Functions で Admin SDK を使い、対象チームに限定してデータを読む。**AI-009（クライアントがコンテキストを組み立てる）は Web チャット能力にのみ適用**とし、バックグラウンド能力には適用しない

#### 能力の呼び出し方（利用者はプロンプトを名前で呼ばない）

| 実行面 | 呼び出し方 |
| --- | --- |
| 画面に埋め込む能力（`playbook_elicitation` など） | 使う場面に置いたボタン・パネルから起動する。「進め方をいっしょに作る」は最初のブリーフの 1枚紙画面に、学習提案は進め方設定画面に現れる。メニューから能力を選ぶ導線は作らない |
| チャット面（`/chat`、`/risukerugg`） | 入力欄は 1 つ。有効な能力を Claude の **tool** として渡し、どの能力を使うかはモデルが選ぶ。能力の `inputSchema` がそのまま tool の入力スキーマになり、能力レジストリと tool 一覧が常に一致する |
| バックグラウンド能力（`playbook_learning`） | Scheduler / Firestore トリガーから起動する。利用者の操作はない |

- チャット面の提案は tool 呼び出しの構造化出力として受け取り、既存の `%%PROPOSAL%%` マーカー解析（AI-011 / IN-018）は載せ替え完了後に廃止する。載せ替え期間中は両方を受け付ける
- 提案の確認・登録の流儀（提案カード / Embed とボタン、Zod 再検証、承認後にのみ書き込み）は変えない

#### チームの定型指示（軽量機能）

チームが繰り返し使う決まり文句（例: 「今週の締切をまとめて」「来週の予定を出して」）を登録し、入力の手間を減らす。大きなプロンプト集にはしない。

- 保存先: `teams/{teamId}/ai/prompts/{promptId} = { name, body, order }`。operator が `/settings/ai` で追加・編集・削除する。上限 10 件
- Web `/chat`: 入力欄の上のチップ（既存 AI-003 の例示チップと同じ位置）に登録順で表示し、押すと `body` を送信する
- Discord `/risukerugg`: 任意オプション `定型` を追加し、オートコンプリートでチームの定型指示を候補に出す。選ぶと `body` を `message` として扱う
- 定型指示は能力ではない。送られた本文に対し、どの能力を使うかは通常どおりモデルが選ぶ

初期の能力一覧:

| id | 実行面 | 内容 | 段階 |
| --- | --- | --- | --- |
| `register_from_text` | Web / Discord | 自然文からスケジュール・タスク・コラボの登録提案（既存） | C-1 で載せ替え |
| `query_team_data` | Web / Discord | チームデータへの質問・スケジュール照会（既存） | C-1 で載せ替え |
| `task_update` | Web / Discord | 既存タスクの編集提案（既存・`feature/ai-improvements`） | 扱いは「未決事項」参照 |
| `playbook_elicitation` | Web | 対話で進め方を引き出し、構造化する | C-2 |
| `playbook_learning` | バックグラウンド | 差分から進め方の修正案を生成 | C-3 |
| ~~`report_interpretation`~~ | Discord | スレッド内の自由文を工程完了の提案に変換 | 見送り（ボタン運用のみ） |

### C-2. 進め方の引き出し

登録時の抽象的な質問ではなく、**最初のブリーフを進めながら**聞く。

1. 進め方が 0 件のチームで最初のブリーフを作成すると、1枚紙画面に「進め方をいっしょに作る」パネルが開く
2. 台本: 「この動画で最初にやることは何ですか？」→ 回答（例: 「サムネを作る」）→ 「誰が担当しますか？」「公開の何日前までに終わればよいですか？」「始めるのに必要な情報はありますか？」→ 工程 1 件が構造化されてプレビューに追加される → 「その次は何をしますか？」を「以上」まで繰り返す
3. 回答は自由文で受け、AI が `StepDef` の構造に変換する。「りすくに構成を確認してから、さとうが作る」のような回答は「構成確認（担当: りすく）」「サムネ作成（担当: さとう、依存: 構成確認）」の 2 工程に分解する。メンバー名は `displayName` から UID に解決する（既存 AI-014 と同じ）
4. プレビューは構造化された工程一覧（表）で、その場で並べ替え・修正できる。「この進め方で始める」で `Playbook` を `origin: dialogue` で保存し、当該ブリーフの工程を生成する
5. 進行中に進め方に無い工程が必要になった場合、工程の手追加時に「進め方にも追加しますか」を聞く

### C-3. 運用からの学習提案

- 毎晩、Cloud Functions が各チームのブリーフの差分（`events`）と生成元の進め方を突き合わせ、次の 5 種類の信号を検出する

| 信号 | 検出 | 提案 |
| --- | --- | --- |
| 実際の順序 | 進め方と異なる順序で完了した工程が複数ブリーフで一致 | `dependsOn` の変更 |
| 実際の担当 | 既定担当と異なる担当への変更が繰り返される | `defaultAssigneeId` の変更 |
| 実際の日数 | 完了日と公開日の差が `leadDays` と継続して乖離 | `leadDays` の変更 |
| 求められた情報 | 工程パネルやスレッドで同じ情報が繰り返し追加入力・質問される | `requiredFields` の追加 |
| 飛ばされた工程 | 同じ工程が繰り返し `skipped` | `optional: true` |

- 検出は決定的（閾値: 直近 3 ブリーフ中 2 回以上）に行い、AI は提案文の生成と「求められた情報」の項目名抽出にのみ使う
- 提案は `teams/{teamId}/playbookSuggestions/{id} = { playbookId, kind, evidenceBriefIds, patch, message, status: pending | accepted | rejected, createdAt }` に保存し、`/briefs/playbooks` に差分として表示。ダイジェストに「進め方の提案が N 件あります」を添える
- operator が承認すると進め方の `version` を上げて反映する。既存ブリーフの工程は変えない

### C-4. 自由文の完了報告解釈（見送り）

- 2026-09-06 の決定により、完了報告は B-2 のボタン運用のみとし、スレッド内の自由文は読まない
- 理由: Message Content Intent が必要になり、導入サーバーが 100 を超えると Discord の審査が要る。ボタンで足りる間は採らない
- 将来検討する場合の条件: 読む範囲をブリーフのスレッド内に限定し、解釈結果は提案としてボタン確認を経る

### 既存 AI チャットの扱い

- `/chat` と「AIに相談」導線は残す。対応範囲（AI-007）は変えないが、ナビゲーション上の位置は「メイン」の末尾に下げる
- タスク詳細からの「AIに相談」（AI-018）は現状維持

### 要件（実装のゴール）

- 「AI に何ができるか」が `/settings/ai` の一覧と `src/lib/ai/capabilities/` の定義で一致して分かる
- プロンプトの変更が版とテストで追跡できる
- 進め方が、設定画面を白紙から埋めることなく、最初の動画を進める中で対話だけで出来上がる
- 3 本目以降の動画から、進め方の修正案が自動で届き、承認だけで反映される

## D. 操作層の一本化と公開 API・MCP 対応

### 内容

RisukeruGG を「各 API や情報基盤の接続基盤」として位置づけるため、アプリ側から API を公開し、将来の MCP サーバーに対応できる形にする。ただし公開 API や MCP を先に作るのではなく、**A〜C を「一つの操作層」の上に作る**ことで、公開 API と MCP が後から薄い皮として載る状態を作る。

### D-1. 操作層の定義（A-1 と同時）

- `src/lib/briefs/operations/` に、ブリーフに対するすべての操作を「入力スキーマ（Zod）・権限条件・実行関数」の組として定義する。例: `createBrief` / `updatePublishAt` / `completeStep` / `assignStep` / `setStepField` / `skipStep` / `addStep` / `listBriefs` / `getBrief` / `listMySteps` / `getDigest`
- Web 画面、Discord のボタン、AI の tool、公開 API、MCP のすべてがこの操作を呼ぶ。入口ごとに書き込みロジックを持たない（設計原則「操作層は一つ」）
- 権限判定は操作層の中で行い、入口が Firestore ルール（クライアント SDK）か Admin SDK（サーバー）かに依らず同じ結果になるようにする。サーバー実行時は NFR-006 のとおり操作層の判定を必ず通す
- 各操作は差分（BriefEvent）の記録まで含めて完結する
- C-1 の AI 能力のうち、ブリーフを扱うものは操作層の操作をそのまま tool として渡す。能力レジストリと操作層の二重定義を避ける

### D-2. 公開 API

- `/api/v1/` 配下に REST API として公開する。対象は D-1 の操作と、既存のスケジュール・タスク（v1）・コラボの参照系から始める
- 認証: `/settings/profile` で発行する**個人アクセストークン**（ハッシュ化して `users/{uid}/apiTokens/{tokenId}` に保存、発行時のみ平文表示）。トークンは発行者の UID として振る舞い、権限は発行者のチームロールに従う。チームは `teamId` をパスまたはヘッダで指定する
- レート制限とトークンの失効・一覧・削除を提供する。レート制限の値は plan カテゴリで決める
- レスポンスとエラーの形式、バージョニング（`v1` 固定、破壊的変更は `v2`）、OpenAPI 定義（`docs/api/openapi.yaml`）を整備する
- Discord Bot は当面 D-1 の操作層を直接呼ぶ（同一デプロイ内のため）。公開 API を経由させる必要はない

### D-3. MCP サーバー

- 公開 API を tool として提供する MCP サーバーを別パッケージ（`packages/mcp-server/`）として提供する。利用者は自分のローカル AI クライアント（Claude Desktop、Claude Code、他の MCP 対応クライアント）にトークンを設定し、「今週の締切を教えて」「サムネ工程を完了にして」を自分の AI から実行できる
- tool の定義は操作層の入力スキーマから生成し、手書きしない。操作を追加すると API と MCP の両方に現れる
- 書き込み系 tool は MCP クライアント側の確認を前提とし、サーバー側では発行者の権限で判定する
- 配布形態（npm 公開か、リモート MCP としてホストするか）は D-2 完了後に決める。リモート MCP を選ぶ場合の認証は OAuth 2.1 が求められるため、そのときに個人アクセストークンとの関係を再設計する

### 要件（実装のゴール）

- ブリーフに対する操作が、Web・Discord・AI のどの入口からでも同じ関数で実行され、同じ権限判定と差分記録を通る
- 操作を 1 つ追加すると、公開 API と MCP tool に追加の手書きなしで現れる
- 利用者が自分の AI クライアントから、自チームのブリーフの参照と工程完了を行える

## E. 法務ページの更新（プライバシーポリシー・利用規約）

### 内容

Discord 連携の強化で取得・送信する情報が増えるため、公開前にプライバシーポリシーと利用規約を改定する。あわせて「本サービスは機密情報の保管を目的としない」方針を明文化し、利用者が入力した機密情報について当方が責任を負わない範囲を定める。

方針（ユーザー決定 2026-09-06）:

- Discord 関連の情報は**取得はするが、Discord 上での取り扱いについて責任は負わない**
- スケジュール・タスク・ブリーフ等に入力された機密情報について、当方は責任を持たない。**基本的に入力しない方針**とし、入力して漏えいした場合は利用者の自己責任とする

### 法的な前提（条文の書き方の制約）

- 「一切責任を負わない」という全部免責は、消費者契約法第 8 条により無効になる。現行の利用規約第 9 条が既に採っている「**当方の故意または重過失による場合を除き**責任を負わない。消費者契約法等で免責が認められない場合は法令に従う」の形式に揃える。この形なら「自己責任」の趣旨は保ちつつ条項が無効になるのを避けられる
- 当方が**保持する**個人情報（Discord ユーザー名・ID を含む）には個人情報保護法上の安全管理措置義務があり、これは免責できない。免責の対象は「Discord へ送信した後の Discord 上での取り扱い」と「利用者が禁止に反して入力した機密情報」に限定する
- 「入力しない」は利用者の義務なので**利用規約の禁止事項**に置き、プライバシーポリシーには「取得する情報」と「Discord への送信」の事実を書く。両者の役割を混ぜない
- 条文は雛形であり、公開前に事業者（ユーザー）自身の最終確認を要する（リリース準備 T3 と同じ扱い）
