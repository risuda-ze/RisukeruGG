# unavailability model

## モデル方針

対応不可は「1 人・1 ヶ月」を 1 ドキュメントにまとめて持つ。1 日は 24 ビットの整数 1 つで表し、追記・人数集計・時間帯フィルタをビット演算で済ませる。コメントは 1 件を 1 ドキュメントで持ち、月ドキュメントには入れない。

所属者の所属とロールは team、アカウントの状態は user を参照する。

## UnavailabilityMonth

Firestore コレクション配置: `teams/{teamId}/unavailability/{userId}_{yyyy-mm}`

| フィールド  | 型 / 例                        | 意味 |
| ----------- | ------------------------------ | ---- |
| `userId`    | string                         | 申告した本人の UID。ドキュメント ID の前半と一致する。ルールの本人確認と、退出時の削除（`userId` の等価条件）に使う |
| `month`     | string / `2026-11`             | 対象月（JST）。ドキュメント ID の後半と一致する。Firestore はドキュメント ID の後半で絞り込めないため、月単位の購読（等価条件）と月次削除（範囲条件）の検索キーとして持つ |
| `days`      | map / `{ "2026-11-14": 15728640 }` | 日ごとの対応不可マスク。キーは `month` に属する日（`yyyy-mm-dd`）、値は下記のビットマスク。対応不可が無い日はキーを持たない |
| `updatedAt` | timestamp                      | 対応不可を最後に保存した日時（サーバー時刻）。一覧の「最終更新」に使う。コメントの投稿では変わらない |

ドキュメントが無いことは「その月は未入力」を表す。`days` を持たない月ドキュメントは、対応不可なしとして扱う。

### 日マスク

- 0〜16,777,215（2^24 − 1）の整数。ビット `h`（0〜23）が立っていれば、その日の `h:00`〜`h+1:00` が対応不可
- 例: 20:00〜24:00 が不可 → ビット 20〜23 → `0xF00000` = 15,728,640。終日不可 → `0xFFFFFF`
- 値が 0 になった日はキーを削除する（0 を保存しない）
- 演算: 追記（CSV・定期入力）は OR、その日に不可があるかは `!== 0`、時間数は立っているビット数、時間帯フィルタは対象時間帯のマスクとの AND が 0 かどうか

## UnavailabilityComment

Firestore コレクション配置: `teams/{teamId}/unavailabilityComments/{commentId}`（`commentId` は Firestore の自動採番）

所属者 1 人の時間帯に付けるコメント。投稿者ごとに書き込み権限を分けるため、1 件を 1 ドキュメントで持つ。

| フィールド     | 型 / 例               | 意味 |
| -------------- | --------------------- | ---- |
| `targetUserId` | string                | コメントを付けた時間帯の持ち主（所属者）の UID。所属者詳細に表示する対象の特定と、退出時の削除（等価条件）に使う |
| `authorId`     | string                | 投稿者の UID。ルールの本人確認（編集は投稿者のみ、削除は投稿者かメンバー）、投稿者名の表示（`TeamMember` を引く。所属していなければ「退出したユーザー」）に使う |
| `month`        | string / `2026-11`    | `date` が属する月（JST）。月単位の購読（等価条件）と月次削除（範囲条件）の検索キーとして持つ |
| `date`         | string / `2026-11-14` | 対象日 |
| `start`        | number / 0〜23        | 開始時（その時を含む） |
| `end`          | number / 1〜24        | 終了時（排他的境界）。`start < end` |
| `text`         | string                | 本文。1〜100 字 |
| `createdAt`    | timestamp             | 投稿日時（サーバー時刻）。同一時間帯のコメントの並び順に使う。編集では変えない |

コメントは対応不可マスクと独立で、同じ時間帯に複数あってよい。投稿者の表示名は保存せず、表示時に `TeamMember` から引く。投稿者が退出した後もコメントは残り、`authorId` は退出したユーザーの UID のまま持つ。

## 制約

- 日付・時はすべて JST。日をまたぐ入力は保存前に日付ごとに分割し、月をまたぐ場合はそれぞれの月ドキュメントに書く
- 保存する月は「前月・当月・翌月」の 3 つまで。前々月以前は、月ドキュメントもコメントも毎月 1 日 0:00 JST に Cloud Functions が削除する
- 通常の保存は、変更した日のキーだけを更新する（月ドキュメント全体を上書きしない）。CSV・定期入力の和集合保存は読んでから書くため、トランザクションで行う
- クライアントは月ドキュメントを消さない。対応不可をすべて消した月は `days` が空のまま残り、`updatedAt` で「入力済み」と分かる
- コメントの `month` は `date` の先頭 7 文字と一致させる。編集で `date` が別の月へ移る場合は `month` も合わせて書き換える
- コメントの `targetUserId` / `authorId` / `createdAt` は作成後に変えない

## Firestore Security Rules

### 月ドキュメント

`teams/{teamId}/unavailability/{docId}` に次を定める（1 ブロック）。

| 操作 | 条件 |
| ---- | ---- |
| read | 同一チームの所属者（ロール不問） |
| create / update | 同一チームの所属者（ロール不問）かつ β ゲート通過。書き込み後の `userId` が本人の UID、`docId` が `{本人の UID}_{month}`、`month` が `yyyy-mm` 形式、フィールドが `userId` / `month` / `days` / `updatedAt` のみ、`days` が map、`updatedAt` がリクエスト時刻 |
| delete | 不可（削除は Admin SDK のみ） |

ルールは map の中身を走査できないため、次はルールでは検証しない。

- 日マスクの範囲（0〜2^24 − 1）、`days` のキーが `month` に属すること
- 入力できる範囲（翌月末日まで）

これらは書き込み前にクライアントの Zod スキーマで検証する。不正値を入れられるのは本人のドキュメントだけなので、読み取り側は同じ Zod スキーマで検証し、通らない日は捨てて表示する（画面全体を落とさない）。

### コメント

`teams/{teamId}/unavailabilityComments/{commentId}` に次を定める（1 ブロック）。

| 操作 | 条件 |
| ---- | ---- |
| read | 同一チームの所属者（ロール不問） |
| create | 同一チームの所属者（ロール不問）かつ β ゲート通過。`authorId` が本人の UID、`targetUserId` が同一チームの所属者（`members/{targetUserId}` が存在する）、フィールドが `targetUserId` / `authorId` / `month` / `date` / `start` / `end` / `text` / `createdAt` のみ、`date` が `yyyy-mm-dd` 形式、`month` が `date` の先頭 7 文字、`start` が 0〜23 の整数、`end` が 1〜24 の整数で `start < end`、`text` が 1〜100 字の文字列、`createdAt` がリクエスト時刻 |
| update | 同一チームの所属者（ロール不問）かつ β ゲート通過で、既存の `authorId` が本人の UID。`targetUserId` / `authorId` / `createdAt` は既存の値から変えない（`createdAt` をリクエスト時刻にし直さない）。フィールドの種類と、`month` / `date` / `start` / `end` / `text` の検証は create と同じ |
| delete | 同一チームの所属者で、既存の `authorId` が本人の UID、またはロールがメンバー。退出時・月次の削除は Admin SDK で行う |

退出したユーザーは所属者でないため、自分が投稿したコメントを更新・削除できない。退出したユーザーのコメントを削除できるのはメンバーだけになる。

次はルールでは検証しない。書き込み前にクライアントの Zod スキーマで検証し、読み取り側も同じスキーマで検証して、通らないコメントは捨てて表示する。

- `date` が実在する日付であること
- 投稿できる範囲（前月 1 日〜翌月末日）

## 読み取り

- 一覧・詳細とも `teams/{teamId}/unavailability` を `month` の等価条件で購読する（1 クエリでチーム全員の 1 ヶ月分）。当月を先に購読し、前月・翌月はスクロールが端に近づいたときに購読を足す
- コメントは、所属者詳細を開いている間だけ、読み込み済みの月ごとに `teams/{teamId}/unavailabilityComments` を `month` の等価条件で購読する（1 クエリでチーム全員宛ての 1 ヶ月分）。表示するのは `targetUserId` が開いている所属者のものとし、`createdAt` の古い順（同値はドキュメント ID の昇順）に並べる。一覧だけを見ている間は購読しない
- 一覧の「最終更新」は、その所属者の読み込み済み月ドキュメントの `updatedAt` のうち最新のもの。読み込み済みの月にドキュメントが 1 つも無ければ「未入力」

## インデックス

- 月次削除はコレクショングループ `unavailability` と `unavailabilityComments` を `month` の範囲条件で引くため、`firestore.indexes.json` の `fieldOverrides` に、それぞれの `month` のコレクショングループスコープのインデックスを追加する
- 退出時の削除（月ドキュメントは `userId`、コメントは `targetUserId` の等価条件）と画面の購読（`month` の等価条件）は自動の単一フィールドインデックスで足りる
