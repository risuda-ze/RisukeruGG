# user flows

## 初回ログインフロー

1. ユーザーがログインページから Google サインインを開始する
2. Firebase Authentication で Google OAuth2 認証を完了する
3. 初回ログインかどうかを判定する
4. 初回ログインの場合は User アカウントを自動作成する
5. 初回所属チームの生成と初期ロール（`member` / `staff`）付与は team カテゴリの初期所属フローへ委譲する
6. 認証済み状態として保護画面へ遷移する

## 継続利用フロー

1. 既存ユーザーが Google サインインする
2. 既存の認証セッションを復元する
3. 必要に応じて認証トークンを自動更新する
4. 最後に利用していた保護画面へ復帰する

## 保護ページアクセスフロー

1. ユーザーが保護ページへアクセスする
2. 認証状態を確認する
3. 未認証の場合はログインページへリダイレクトする
4. 認証済みの場合はそのまま画面を表示する

## Google カレンダー書き出しの認可フロー

1. ユーザーが Google カレンダー書き出しを開始する
2. `calendar.app.created` スコープを付けた Google 認可ポップアップを開く（ログイン時にはこのスコープを要求しない）
3. ユーザーが同意すると、その場限りのアクセストークンを取得して書き出し処理へ渡す。トークンは localStorage・Firestore へ保存しない
4. ユーザーが拒否した場合、またはログイン中と別の Google アカウントを選んだ場合は、エラーを表示して書き出しを行わない

## アカウント削除フロー

1. ユーザーがアカウント削除を実行する
2. Firebase Auth 上の認証アカウントを削除する
3. `users/{uid}` ドキュメントを完全削除せず、ゴースト状態へ変換する
4. `displayName` と `avatarUrl` など過去データ表示に必要な最小情報のみ残す
5. 個人情報と運用情報を削除する
6. 所属していた全チームから、本人の対応不可と、本人の時間帯に付いた対応不可コメントを削除する（[unavailability/flows.md](../unavailability/flows.md)）。本人が他の所属者の時間帯に投稿した対応不可コメント（本文と投稿者の UID）は削除せず、月次削除で消えるまで残る。削除に失敗してもアカウント削除は成立させる
7. ghost User は復元対象にせず、履歴参照用として残す

## 削除後の再サインインフロー

1. 過去に削除された Google アカウントで再度サインインする
2. 既存の ghost User を検索しても、それを active へ復元しない
3. 新しい active User を新規作成する
4. 初回所属チームの生成と初期ロール（`member` / `staff`）付与は team カテゴリの初期所属フローへ委譲する
5. 旧 ghost User は過去データ参照のためそのまま残存させる
