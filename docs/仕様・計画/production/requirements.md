# production requirements

## 画面と導線

- **PD-001**: サイドバー「メイン」およびモバイルの「その他」ドロワーに「タスク管理 v2」（`/briefs`、β バッジ付き）を設ける。既存「タスク管理」（`/tasks`）はそのまま残す
- **PD-002**: `/briefs` はブリーフ一覧。カードに公開予定日・進捗（完了 + スキップ / 全工程）・次の工程と担当・注意（遅延・入力待ち・担当未定の件数）を表示する。フィルタは「進行中」「自分が関わる（出演者または担当工程あり）」「すべて」
- **PD-003**: `/briefs/{briefId}` は 1枚紙。見出し（タイトル・公開予定日・状態・出演者・見出し項目）と工程一覧を本文に置き、工程の詳細（入力項目・コメント・状態操作）は工程パネル（PC は右ドロワー、モバイルは全画面）で開く。**本文には工程の状態・担当・締切以外を置かない**（1枚は1枚）
- **PD-004**: `/briefs/mine` は自分の工程一覧。全ブリーフの自分が担当する未完了工程を締切順（締切なしは末尾、同日なら着手可能を先）に並べ、各行から 1枚紙の該当工程へ遷移できる
- **PD-005**: `/briefs/playbooks` は進め方設定。進め方の一覧・作成・編集・削除。編集では工程の並び替え、既定担当、役割、公開日からの日数、先行工程、必要情報、リマインド日数、任意工程を扱う

## ブリーフ

- **PD-010**: ブリーフの作成はタイトル・公開予定日（任意）・進め方（任意）・出演者で行う。進め方を指定した場合、工程・既定担当・締切（逆算）・必要情報の定義が埋まった状態で生成し、状態は `in_progress` とする。進め方なしなら工程 0 件の `planning` で作る
- **PD-011**: ブリーフは生成元の進め方の ID と版（`playbookVersion`）を記録する。進め方の後の変更は既存ブリーフに影響しない
- **PD-012**: 見出しの編集（タイトル・状態・出演者・見出し項目）は即時保存し、変更を差分として記録する
- **PD-013**: 1枚紙の「この流れを進め方にする」から、現在の工程（担当・日数・先行・必要情報）を `origin: derived` の進め方として保存できる
- **PD-014**: 「変更の記録」で差分（直近 50 件）を新しい順に表示する。表示は操作者名（Discord 由来は「Discord」、自動は「自動」）と内容の一文とする

## 締切

- **PD-020**: 工程の締切は `publishAt − leadDays`（日付単位、0 時に正規化）で計算する。公開予定日が未設定なら締切なし
- **PD-021**: 公開予定日を変更すると、`dueDateOverridden = false` の全工程の締切を再計算する。画面では保存前に「工程ごとの変更前 → 変更後」を差分プレビューとして表示してから確定する。再計算は差分に `system` 由来として記録する
- **PD-022**: 工程の締切を手で変えると `dueDateOverridden = true` となり、以後の再計算から外れる。工程パネルの「固定を解除」で再計算対象に戻し、公開日から計算し直す

## 工程の状態

- **PD-030**: 状態は `waiting` / `ready` / `in_progress` / `done` / `skipped` の 5 値で固定する（列設定は持たない）
- **PD-031**: `dependsOn` の先行工程がすべて `done | skipped` になった時点で `waiting → ready` へ自動遷移する。差し戻しなどで先行が未完了に戻った `ready` は `waiting` に戻す。参照先が削除された先行工程は満たされたものとして扱う
- **PD-032**: 手動遷移は `ready → in_progress`（着手）、`ready | in_progress → done`（完了）、`ready | in_progress | waiting → skipped`（`optional` の工程のみ）、`done | skipped → ready`（差し戻し）に限る。`waiting` への手動遷移はできない
- **PD-033**: `done` にした工程は完了日時と完了者（Discord 由来は null）を記録する
- **PD-034**: `ready | in_progress` で必須項目（`requiredFields` のうち `required`）が未入力の工程は「入力待ち」として表示し、催促先は項目の `ownerRoleLabel`、なければブリーフ作成者とする（催促の送信は integration）
- **PD-035**: 一覧・工程行では「N日超過」「今日」「あとN日（2 日以内）」「入力待ち」「担当未定（`waiting` 以外で担当なし）」を注意バッジとして表示する。完了・スキップ済みには出さない

## 工程の追加・削除

- **PD-040**: 工程は 1枚紙から手で追加できる。キーは `custom_N`（既存と衝突しない最小の N）、締切は公開予定日から逆算、先行工程は既存工程から選ぶ。先行がすべて完了していれば `ready`、そうでなければ `waiting` で作る
- **PD-041**: 工程を削除すると、他の工程の `dependsOn` から当該キーを外し、依存関係を再評価して自動遷移を適用する

## 進め方

- **PD-050**: 進め方は `name` / `origin`（`dialogue` / `manual` / `derived`）/ `headerFields` / `steps` / `version` を持つ。更新のたびに `version` を +1 する
- **PD-051**: 工程キーは進め方内で一意とし、`dependsOn` は同じ進め方内の他の工程キーのみ参照できる（自己参照不可）。違反する保存は拒否する
- **PD-052**: 進め方の削除は作成済みのブリーフに影響しない

## 操作層（D-1）

- **PD-060**: ブリーフ・工程に対する操作（作成、見出し更新、状態変更、担当変更、締切変更、項目入力、工程名変更、工程追加、工程削除）は `src/lib/briefs/operations` に「権限判定 → 現状読み込み → 変更の計画（純粋関数）→ 差分記録 → commit」の順で定義する。Web 画面・Discord・AI・公開 API はすべてこの操作を呼び、入口ごとに書き込みロジックを持たない
- **PD-061**: 操作は永続化ポート（`BriefsPort`: `newId` / `loadBrief` / `commit`）に依存し、クライアント（Firestore SDK の writeBatch）・サーバー（Admin SDK）・テスト（メモリ）が同じ契約を実装する。1 操作は 1 トランザクション（ブリーフ更新・工程の作成/更新/削除・差分追記）として原子的に適用する
- **PD-062**: 権限は [team/model.md](../team/model.md) の権限の表に従う。ブリーフの作成は所属者全員、編集はメンバーか作成者、削除はメンバーのみ。工程の追加・削除と担当・締切・入力項目の変更はブリーフの作成者かメンバー、完了・状態変更は担当者本人も可。Discord・システム由来（`source: discord | system`）はサーバーに居ることを信頼境界として許可し、`actorId` は null で記録する
- **PD-063**: 変更のない操作（同じ値での更新）は commit しない

## 権限・データ

- **PD-070**: Firestore ルールで `playbooks` / `briefs` / `steps` / `comments` / `briefEvents` の読み取りは所属者全員とする。書き込みは PD-062 の権限をルールでも強制する（`playbooks` はメンバーのみ）。加えて、工程の変更に伴ってブリーフの `updatedAt` だけを進める更新と、先行工程の再評価による工程の「待機」と「着手可能」の間の自動遷移（`status` と `updatedAt` だけの更新）は、所属者全員に許す。`briefEvents` は所属者が追記でき、改変・削除は不可。コメントの作成は所属者全員、更新・削除は本人またはメンバー
- **PD-071**: 自分の工程一覧・ダイジェストのため、`steps` は `teamId` を持ち、コレクショングループで `teamId` 一致のみ読めるようにする
- **PD-072**: 差分のサブコレクション名は `briefEvents` とする（汎用名 `events` は使わず、コレクショングループ購読時に他用途のサブコレクションと衝突させない）
- **PD-073**: プラン上限は当面設けない（値は保留。判定箇所は plan カテゴリで用意する）
