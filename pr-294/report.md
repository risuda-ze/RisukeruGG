## 人が確認すべき点

1. マージ前にリベースが要る。スタック元の #282 は既に develop に入っており、先にマージする注意は不要になった。一方、この PR のブランチは develop より遅れている。develop 側の #298 も同じ共通処理のファイルを変更しているので、リベース後の内容を見てほしい。リベースだけで変更内容が同じなら再レビューを求めない検査（#298）が develop に入っている
2. guard の変更は取り下げた。そのため、最終レポートの本文にはコマンドの記述をそのまま書けないという運用上の制約が残る（マージやリモートへの反映のコマンド名、hook を飛ばす指定、レビュー判定のマーカーなど。対象は final-report スキルの表）。書くと拒否され、言い換えて再実行することになる。報告の文面が回りくどくなる点を含め、根本の対応は #291 が追跡している
3. 標準入力での実投稿の確認。この最終レポートは、Windows 11 上で、二次レビュー担当が PR のチェックアウト（8286208）から、スキル記載のとおり Bash のヒアドキュメントと標準入力の指定で投稿した。本文のファイルは別の手段で作っていない。このコメントが PR に付き、レポート用ブランチに pr-294 のディレクトリがあれば、#244 の「Windows で実際に実行し、PR コメントの投稿まで通す」は確認できたことになる。投稿後の確認結果（ブランチへの反映とコメント）と、guard に拒否された回数は、二次の担当がオーケストレーターへの報告に書く
4. 実リポジトリでは確かめられなかった点。レポート用ブランチは既に存在するので、初回のブランチ作成はユニットテストだけが根拠になる。初回に失敗した後の再実行は #299 のとおり未対応
5. PowerShell ツールからは本文を渡せない（ヒアドキュメントを使えない）。スキルに「Bash で渡す」と書いてあり、対応は入れていない
6. 推奨にとどめた点。スキルの表には、パス指定つきでリモートへ反映する形と、レビュー判定のマーカーを含むファイルを本文として指定する形が載っていない。直すかどうかは任意
7. #299 と #300 は未対応のまま open。#300 は GitHub 側の保護設定が最後の防衛線になる
