# 変更仕様テンプレート

## 変更名

一意な名前（kebab-case のファイル名にもなる）。

## 目的

何のために変えるか。誰（配信者 / チームメンバー / 運営）のどの困りごとを解消するか、1〜2文。

## 対象範囲

- 含む: 機能・画面・API
- 含まない: 今回触らないことを明示

## 正本仕様との関係

- 参照: `docs/仕様・計画/<カテゴリ>/<ファイル>` の該当節
- 仕様変更の有無: なし / あり（変更内容と、実装後に更新する正本ファイル）

## 受入条件

| ID   | 入力・操作 | 期待結果 |
| ---- | ---------- | -------- |
| AC-1 |            |          |

## 設計

実装者が設計判断をしなくて済む粒度で書く。該当しない項目は「変更なし」と書く（省略しない）。

- データモデル: Firestore のコレクション・フィールドの追加/変更、型（`src/types/`）、既存データの移行要否
- アクセス制御: `firestore.rules` / `storage.rules` の変更、権限をどこで強制するか（クライアント / Functions）
- インデックス: `firestore.indexes.json` に必要なクエリとインデックス
- 処理の流れ: 操作 → クライアント → Functions / 外部サービス → 保存 の順序と、各段の失敗時の挙動
- 再利用: 使う既存の関数・コンポーネント・ストア（パス）。新規に作るものとその理由
- 互換性: 既存の画面・API・通知への影響、段階リリースの要否

## 影響ファイル（想定）

- `src/...` / `functions/src/...` / `tests/unit/...`

## 制約・注意

権限（ロール）・プラン制限・JST・外部サービス（Discord / Stripe / メール）失敗時の扱いなど、該当するもの。

## 根拠・仮定

- Issue・ユーザー指示のどこを根拠にしたか
- 置いた仮定と、ユーザー確認が必要な点。比較した案があれば採用理由

## 用語追加候補

無ければ「なし」。
